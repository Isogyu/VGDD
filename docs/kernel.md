# VGDD Governance Kernel — 設計方針（ADR-001〜033）と実装の対応

- 作成：2026-11-05（開催期間中に新規作成）
- 規範：`vgdd/kernel/SPEC.md`（言語に依存しない規範）、`vgdd/kernel/capabilities.json`（役割と権限の表）、`vgdd/schemas/kernel-decision.schema.json`（判定の記録）
- 適合性テスト：`node vgdd/conformance/run.mjs`（オーナーか立法補佐が sandbox の外で実行。依存なし）
- 出どころ：ADR-001〜033 は、オーナーが別の AI との対話（ヒアリング）で整理し、2026-11-05 に採用した VGDD の設計方針。この文書は、それを今の VGDD の実装に対応づけたもので、Claude（立法補佐）が書いた。ADR の本文はリポジトリに置いていない

## 1. 何が変わったか

VGDD は「複数の AI に役割を与えて開発する仕組み」から、**役割の権限を Governance Kernel が技術的に強制する開発方法論**として整理し直した。

- **Kernel は第4の権力ではない。** 判断しない。あらかじめ決めた権限・規則・承認の条件を強制するだけ（判定は司法、決定は主権者）
- **境界はプロンプトでなく実行環境で強制する。** 強制していない約束は、権限の表に `promise` と書いて公開する
- **最初に作るのは小さな Kernel。** 33件を一度に実装しない。成立条件①〜⑤を強制し、それを試験で示せる状態を先に作る

## 3. 成立条件①〜⑤と、適合性テスト

|---|---|---|---|

| ③ 独立司法 | 司法の入力を機械的に集め、行政の説明を入れない。司法はツールなし。main の §2 だけ | C3（10件） | 10/10 |
| ④ Kernel による強制 | 統合は裁判所だけ。未承認・司法の不合格・保護パス・範囲外・停止中は main に入らない。統治の項目は申請ごとに固定した main の票から読む。行政の長の main への直接コミットは docs/ の下だけ | C1 の統合系、G1〜G10、H1〜H10 | 合格 |
| ⑤ 証跡の追跡 | 判定ごとの記録（誰が・何を・どう・なぜ）、ハッシュチェーン、チェックポイント | A（7件）、K の R1・R2 | 合格 |

- 合計 **273件に合格**（C1 105、A 8、C2 16、C3 10、G 18、ST 8、K 21、H 10、N 5、L 5、M 67。p0.4.3）。G14〜G18（司法が使えないことを判定として扱わない：起動時の点検、Codex が判定のファイルを書かない、同じ申請で3回、前の申請の判定を使わない、戻った後の陽性の対照）と ST（Kernel の状態の写し）は p0.4.3 で足した。**p0.4.2 の実装では G15 で、Codex の判定がないまま judge の APPROVED だけで統合された**（判定のファイルがないことを SKIPPED とみなし、minor の不一致として扱っていた。行政の長 Max の夜の点検で見つかった）。p0.4.2 の実装では新しい 31 件だけが落ちる
- p0.4.2 のとき：合計 231件に合格（C1 90、A 8、C2 16、C3 10、G 13、K 21、H 10、N 5、L 5、M 53。p0.4.2）。G11〜G13（申請中の票に他人の書きかけがある間・票が未追跡の間は、裁判所はその申請を処理しない。書きかけがコミットされた後は普通に処理する）と G9 の改め（作業ツリーで files_allowed を広げた票も書きかけとして処理しない）は、昼の運用で立法補佐の書きかけが裁判所のコミットに入った件（OBS-050）を受けて p0.4.2 で足した。p0.4.1 の実装では G9・G11・G12・G13 が落ちる（G13 では、前の版の裁判所が未追跡の票を自分の名前で main にコミットした）。L（朝の統合 release.sh）は V8 の朝に見つかった同時実行の問題（OBS-048）を受けて p0.4.1 で足した。p0.4.0 の実装では L1・L2・L4 が落ちるG は本物の gate-runner に代わりの司法をつないで、UTF-8 のロケールで動かした（OBS-043 の教訓）
- **試験が空回りしていないことの確認**：同じ試験を、今動いている前の版（Z3 の p0.3.2a。仕様の承認と停止の仕組みがない）にかけると **147/218**。落ちたのは新しい規則の試験だけ（C2 15件、G1・G4・G5・G9・G10、K 16件、H 7件、N 3件、それらを参照する M 25件。計71件）。**前の版では、仕様が未承認の票も、承認の後に受け入れ条件を書き換えた票も、main の checkout でコミットせずに files_allowed を広げた票も統合された**（G1・G4・G9）。成立条件②の穴が実在したことの実証
- **別系統の監査**：p0.4.0 の初版を Codex（読み取り専用）に監査させ、16件の指摘を受けた（critical 4・major 11・minor 1）。指紋の符号化の衝突と重複キー、作業ツリーの票を読む穴、照合と使用の時刻の差、停止中の Bash、再開の作者名への依存と巻き戻し、行政の長の main への直接コミット、試験の空回り（スキーマの検証・終了コード・夜間の試験の欠落）を直し、それぞれを判例として試験に加えた。わたし（立法補佐）の手直しで夜間の時刻の上限を壊していた誤り（#11）も Codex が見つけた。残りは既知の課題（下の §6）
- **本番の運用で見つかった穴**：gate-runner の記録のコミットが `docs/tasks/` を丸ごと add しており、立法補佐のコミットしていない `docs/tasks/README.md` の編集が gate-runner の名前で main に入った（2026-11-05 21:39、OBS-044）。裁判所の名前で他人の変更を main に入れる経路で、作者名で数える事後検知もすり抜ける。p0.4.0 で、裁判所がその周回に自分で書き換えた票だけをコミットするように直した（G10）
- 「VGDD Core に適合」とは名乗らない（SPEC §11）。名乗れるのは「この構成で、適合性テスト 228件に合格」まで

## 6. 保証できないこと・既知の課題

- 停止は、停止の前に始まって実行中の処理（長い Bash、夜間の作業員、司法の呼び出し）を強制終了しない
- 複数のオーナー側のプロセス（gate-runner・night-runner・release・承認・停止）にまたがる排他は、停止と再開の錠と release の錠だけ（gate-runner と release の間は、gate-runner が統合の直前に main の前進を確かめて検査し直すことで扱う）。障害からの回復の手順は未
- 実行の主体の証明は、AI はフックの入力と起動の仕方、スクリプトはプロセスの権限による。git の作者名は本人確認にならない
- 適合性テストは写しのリポジトリとフックの単体で動かす。実際の sandbox・実際の起動設定（Claude Code の権限ルール、worktree isolation）は、V6・V7 の実セッションの記録で確かめたもので、この試験の範囲外

`vgdd/kernel/SPEC.md` §12 と `docs/vgdd-status.md` の限界の節のとおり。特に、同じ機械の管理者権限（オーナー）は Kernel と記録を変えられる。強い保証には外部の信頼基盤が要る。
