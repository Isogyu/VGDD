# つぶやき業務ログ（README の下書き）

> **下書き**（2026-11-06 02:4x、行政の長 Max）。数字は main の記録（`docs/`・試験の実行結果）から取った。推測で書いた箇所はなく、確かめていないことは「未確認」と書いた。提出の前にオーナーが確かめて `README.md` に移す。Codex は未点検。

新卒1年目のエンジニアが、作業中に「つぶやく」だけで、あとから **何につまずき・何を試し・どう判断したか** が整理され、本人が承認したものだけがチームの知恵になるアプリです。Built with Claude: Japan 2026 の提出作品で、開発そのものを **VGDD（統制つき開発。Governance Kernel）** のもとで AI のエージェントが行いました。

## 1. 何が起きるか（3分の流れ）

1. **作業開始**（S-1）：作業名を入れる。同じ作業名でチームに承認済みの知恵があれば、開始の時点で出る
2. **つぶやく**（S-1）：作業中のメモを1行ずつ送る。顧客名・メール・電話・カード番号らしい文字列・API キーの形は、保存のたびに**決定論的な検査**で警告が付く（保存は止めない）
3. **いまの理解を整理**（S-1）：進行中でも押せる。「確認済みの事実／AI の推測／未確認／人に確認すべきこと」の4区分と、先輩への質問文の下書き
4. **作業終了 → AI 整理**（S-2）：つまずき・原因・試したこと・解決・判断の理由・学び。項目ごとに根拠のメモへたどれ、根拠のない内容は「AI の推測」と表示
5. **チームに共有する**（S-3）：整理結果から共有候補を作り、機密の検出箇所には**抽象化の案**（顧客A社・プロジェクトX）を本人が選んで置き換える。「AI でも確かめる」で Claude が追加の候補を挙げる（決定論的な検出は AI で減らない）。そのまま承認・編集して承認・却下
6. **チームの知恵**（S-4）：承認済みの共有だけが作業名ごとに並び、2件以上あれば**手順書の原案と判断のポイント**を根拠つきで生成（「原案。利用前に本人・先輩の確認が必要」を常に表示）
7. **統治のライブ画面**（/governance）：この開発で AI の作業員・裁判所・司法がどう動いたかの件数と、票ごとの経過

## 2. 動かし方

前提：Node.js 24 以上（SQLite は Node 組み込みのものを使う。Docker・外部 DB なし）。

```bash
npm ci
npm run dev          # http://localhost:3000
npm run seed         # 開発サーバーが動いている状態で、合成データを入れる（2回目以降は増えない）
npm run seed -- --reset   # 入れ直す
```

- 最初に開く画面は `/`（S-1）。画面上部のセレクタで新人A を選ぶ（既定）。DB（SQLite のファイル）は初回の起動時にスキーマから作られる（**未確認**：クリーンな clone から README だけで動かす通しの試験は提出前にオーナーが行い、結果をここに書く）
- **API キーなし（デモモード）**：AI 整理と手順書の原案は、**保存済みの Claude の出力（fixture）を再生する**。合成データ W1〜W3 の整理結果は `src/lib/demo-fixtures/final-*.json`（実 API、Sonnet 5.5 の出力）。**任意のつぶやきに対して AI が動くわけではなく**、W1〜W3 以外の作業や fixture のない場面は「デモモードでは保存済みの結果がありません」と出る。手順書の原案と「AI でも確かめる」の fixture は **未採取**（T-020 の仕組みで採る。採った後に書き換える）
- **API キーあり**：`.env.local` に `ANTHROPIC_API_KEY=sk-ant-...` の1行を置くと Claude（`src/lib/ai/claude.ts` の `CLAUDE_MODEL`）を呼ぶ。送るのは本文（メモ・共有候補・承認済みの共有）で、送信先は Anthropic の API。費用はキーの持ち主に。失敗時は画面に固定の文（例外の本文は出さない）。`.env.local` はリポジトリに入らない（`.gitignore`）。開発のエージェントもこのファイルを読めない（sandbox の `denyRead`。`docs/vgdd-status.md` V6 #11〜13）
- 試験：`npm test`（vitest。2026-11-06 02:39 の main で **22 ファイル・268 件**合格。提出前に取り直す）、`npm run typecheck`、`npm run lint`

## 5. 保証できないこと（アプリ）

- 機密の検査は**パターンの照合**で、取りこぼしがある。完全な匿名化はしない（画面にも常に表示）
- AI の出力の正しさは保証しない。「AI の推測」「原案」の表示で区別する。手順書の原案は本人・先輩の確認が前提
- デモモードの原案の fixture は、承認済みの共有の内容が変わると「一致しません」になる（T-020 §3 の既知の限界。指紋から番号を外す票を下書き中）
- 音声入力（M13）は未実装（票の下書きのみ）。M11 知らないことマップ・M12 先輩インタビュー・M14 30分チェックインも下書きのみ
- ブラウザーでの動作確認は、オーナーが手元の Chrome で行った範囲（**各票の統合後の確認はこの README の時点で未確認の票がある**：T-014・T-015・T-017〜T-021 の画面はユーザー役の確認待ち）
- Playwright 等の画面の自動試験はない。試験は vitest の単体・結合（SQLite はメモリ）
- 画面上部のユーザーの切り替えは**認証ではない**（誰でも新人A・新人B・先輩C になれる。要件 §4「ログイン・認証は作らない」）。API の認可は要求の `userId` の申告に依る
- **合成データで使うもの**。実在の人の情報や業務の本文を入れた場合の保護は設計していない（検査は警告だけ、API キーがあれば本文が外部に送られる）
- DB はローカルの SQLite ファイル1つ。同時に複数人で使うこと、ほかの端末との共有、バックアップは考えていない
- 動作を確かめたブラウザーは Chrome（オーナーの手元）だけ。ほかは未確認

## 6. VGDD：この開発をどう統制したか

このアプリは、AI のエージェントに**役割**（行政の長・作業員・司法・裁判所・立法補佐）を与え、役割の境界を**プロンプトではなく実行環境**で強制する方法（VGDD、Governance Kernel）で開発しました。詳しくは `docs/governance.md`・`docs/kernel.md`・`docs/vgdd-status.md`。

- **強制の層**（実装と検証の状態。出どころは `docs/vgdd-status.md` §1・§2。**審査員の環境では再現できないもの**：フックの実体と Z3 は作業フォルダの外にあり、オーナーの環境だけ。リポジトリにあるのは原本 `vgdd/` と設定 `.claude/settings.json`）：

  | 層 | 何を止めるか | 状態 | 検証 |
  |---|---|---|---|
  | Claude Code の権限ルール（`.claude/settings.json`） | 保護パスへの Edit・Write・Read | 実装済み | 実セッションで拒否を確認（vgdd-status §2 の 1・3・9・10） |
  | PreToolUse フック `policy.mjs`（原本 `vgdd/hooks/`、実体は Z3） | 全ツール呼び出しの判定と記録。動かなければ全操作が止まる（fail-closed） | 実装済み（p0.4.2） | 実セッションで Bash の拒否を確認（§2 の 2・3、V7 の再試験）。フックを無効にした場合に全呼び出しが止まることも確認（V6 #4） |
  | macOS の sandbox | Bash の書き込み先・読み取り先（`.env.local`・Z3） | 実装済み | 文字列照合を回避した書き込みと Z3 の読み取りを OS が拒否（§2 の 6・7・8） |
  | worktree の分離 | 作業員が main の checkout に書けない | 確認済み | V7 の再試験（閉じ込め①〜③） |
  | 別プロセスの裁判所（gate-runner・release） | 統合は裁判所だけ。夜間は hold | 実装済み（本番で運用） | 2026-11-05〜06 の統合の記録（各票の §6） |
  | Z3（作業フォルダの外の保護領域） | 承認・判定・証拠ストアを行政が読めない・書けない | 実装済み | §2 の 8、V7-7 |
  | 適合性テスト（`vgdd/conformance/run.mjs`） | 権限の表から試験を生成し、止めるべき操作が止まり通すべき操作が通ることを写しの上で確かめる | 実装済み | 下の数字 |

  `CLAUDE.md` の「PreToolUse フックと Z3 の構成は予定（未実装）」の記述は 11/3 時点のもので**古い**（提出前にオーナーが更新する。`CLAUDE.md` は法律の一部で行政は書かない）
- **仕様の統治**：票（受け入れ条件）は main に固定し、オーナーが指紋を承認した記録だけが効力を持つ。承認のない申請は司法の前に止まる（実例：T-016、2026-11-05 23:44）
- **独立した司法**：judge（Claude、ツールなし）と Codex（別系統）が、差分と票の条件と監査の結果だけで判定。分かれたらオーナーの裁定（実例：T-017・T-014・T-019）
- **統合は裁判所だけ**：夜間（`--hold`）は合格しても統合せず、オーナーが `release.sh` で承認して統合（実例：2026-11-05 23:25〜11-06 01:49 に T-010〜T-021 の 12 票。各票の §6 の `release:` の行）
- **数字**（出どころと取得時刻つき。提出の直前に取り直す）：

  - 差し戻し・不一致の件数は `/governance` の「統治の数字」と `docs/tasks/_board.json`（裁判所が書く。**release の後は作り直されない既知の課題**があり、提出前に裁判所の周回で更新されたものを使う）

- **保証できないこと（VGDD）**：フックの Bash の判定は文字列照合で回避の余地がある（書き込みは sandbox が最後に止める）／人が承認画面で許可した操作は止められない／同じ機械の管理者権限は Kernel と記録を変えられる／司法（LLM）の判定の正しさは保証しない／「VGDD Core に適合」とは名乗らない（名乗れるのは「この構成で適合性テスト N 件に合格」まで）。全文は `docs/vgdd-status.md` と `vgdd/kernel/SPEC.md` §12
