## 1. 誰の、どんな課題か

- **今の実証の対象**：複数の開発 AI に作業を任せ、仕様の承認と統合の判断を1人で担う開発者（作者自身。この7日間の記録）
- **新しいペルソナ（仮説・未検証）**：業務は分かるがコードの良し悪しは判断できない業務改善の担当者。IT の担当者が統治の環境を置き、業務の担当者が目的・条件・重要な変更・動作を確かめる。初心者が使えるかは、開発の経験のない人が答えの誘導なしに試すまで未検証と書く

## 2. 台帳（唯一の正本）と実行の記録

- 正本は Z3 の台帳 `~/tsubuyaki-z3/budget/ledger.jsonl`（追記だけ、ハッシュチェーン）。実行の記録は台帳から作り直す派生物で、正本にしない（致命1）
- 台帳の出来事：`request`（論理の要求。重複の防止の ID `req_id`）、`reserve`、`start`（実行の ID `run_id`）、`exit`（終了を確かめた）、`usage`（利用量）、`settle`、`cancel`、`reconcile`（オーナーの照合）
- 各出来事は一意の `event_id` を持ち、同じ `event_id` の二度目の追記は効かない（何度送っても一度だけ効く）。状態の遷移は、追記の前に台帳から作り直した今の状態で検査し、許されない遷移は書かない
- 追記は1つのロック（`mkdir` のロック）の下で、「台帳を読む → 遷移を検査する → 追記する → fsync」を1つの処理にする。台帳の途中切れ・鎖の破損・ロックの取り残しを見つけたら、新しい起動をすべて拒み、オーナーの照合を待つ
- 状態（派生）：`requested` → `reserved` → `started` → `exited` → `settled`。`cancelled` は起動の前だけ。**「利用量が不明」（`usage_unknown`）と「生死が不明」（`liveness_unknown`）を分ける**（重大4）
  - 生死が不明（`start` の後に `exit` がないまま窓口が再起動した）：その票の新しい起動と、その同時の数の枠を解放しない。プロセスの ID と開始の時刻で生存を確かめられたら `exit` を書く。確かめられなければオーナーの照合
  - 利用量が不明（`exit` はあるが `usage` を読めない）：**予約の全量を使ったものとして数える**（0 にしない）。オーナーの照合で直せる
- 同じ `req_id` の二度目の `request` は、前の要求が `settled`・`cancelled` でなければ拒む（重複の起動の防止）

## 4. 昼夜共通の起動の窓口（オーナーの判断1）

- 窓口は Kernel のスクリプト `vgdd/scripts/launch-worker.sh`（Z3 に写して実行。開発エージェントは Z3 を読み書きできないので、窓口は**キューを見る常駐の Kernel のプロセス**として動かす）
- 行政の長は、起動の申請を `merge-requests/launch/T-NNN.json`（票の ID・作業員の数1・申請者だけ）に置く。中身に指示の文を書かない
- 窓口は申請ごとに確かめる：①仕様の承認が今も有効 ②`files_allowed` が保護パスを含まない ③停止中でない ④`depends_on` がすべて merged ⑤予算の予約が取れる ⑥同時の数の枠が空いている ⑦同じ票の起動が生きていない。どれか1つでも欠ければ起動せず、理由を公開してよい区分（`spec_unapproved` など）で返す
- 窓口は、承認済みの票（main の該当コミット）から作業員への指示を組み立て、隔離した worktree で `claude -p --agent worker --max-turns 80` を、45 分の時間の上限で起動する
- フックは `worker`・`tester` の Agent ツールでの起動を拒む（申請の窓口へ案内する文を返す）。ほかの Agent（調べもの・点検）は今のまま許し、**管理の外**として集計だけ出す
- 夜間の運転（`night-runner.sh`）も、作業員の起動をこの窓口に通す
- **強制できない範囲**：行政の長がメインのセッションで自分でコードを書くこと（作業員を使わない作業）は窓口を通らない。ただし今のとおり、main に入るには裁判所と release だけ

## 5. 自動修正の共通化

- 差し戻しのとき、窓口は同じ票で次の試行を起動する（1票3回まで。差し戻しの上限3回とは別に数え、先に達した方で止める）
- 作業員に渡す理由は、Kernel が「この票・この申請の判定」の `findings` から `requirement_id`・`severity`・`category`・相対パスと行番号・短い理由（長さの上限あり）だけを取り出し、絶対パス・秘密らしい文字列の検査を通したもの。検査に落ちたら自動修正をせず人へ戻す。理由は診断の材料で、§2 を変える権限を与えない（重大7）
- §2 の矛盾・依存の追加・禁止の操作が要る、重大な不一致、司法の不調の上限、予算の上限、停止中：自動修正をせず人へ戻す
- 夜間の held と release の条件は変えない

## 6. 要件確認（オーナーの判断5）

- **データは LLM から独立**：質問の項目（固定の型）、回答、未解決の事項、受け入れ条件の候補、承認の状態を、アプリのローカルの SQLite（`data/`、Git に入れない）に持つ。AI の提案と本人の回答は欄を分ける
- **固定の質問だけで使える**：課題 → 動作（入力・結果・例外・反例）→ 制約（データ・外部送信・対象外）→ 確認（未解決の一覧）→ 承認の前の要約。着手に欠かせない項目（目的・正しい結果の例・対象外）が空なら「下書きにできない」と出す。AI なしで十分になるわけではないので、未確認の事項をいつも出す
- **AI の補助（任意）**：最初の接続は Claude Code。オーナーが端末で `vgdd/scripts/req-assist.sh <id>` を動かすと、窓口を通して `claude -p`（ツールなし）に要件のデータを渡し、不足の指摘・追加の質問・受け入れ条件の候補を JSON で受け取り、「AI の提案」の欄に入れる。アプリのサーバーから AI を呼ばない（重大8：アプリは Z3 も AI も触らない）
- **承認の状態**：要件から作った票の下書きを、立法補佐が票にし、オーナーが今の `approve-spec.sh` で承認する。アプリは承認の状態を Kernel の写し（`approvals`）から読んで表示するだけ
- **AI 接続の契約**（§7）を満たせば、ほかのクラウド AI やローカル LLM に替えられる。未検証の接続は「対応済み」と書かない。ローカル LLM は言い換え・要約の下書きにだけ任意で使い、届かなければ省略する（クラウドへ回さない）

## 7. AI 接続と OS 接続の契約

### AI 接続

| 項目 | 契約 |
|---|---|
| 入力 | 標準入力の文（役割ごとに決まった材料だけ） |
| 出力 | 役割ごとの JSON のスキーマ。判定と利用量は別に保存する |
| 利用量 | 窓口が CLI を直接囲んで読む。数えた欄の名前と値。読めなければ「不明」（0 にしない） |
| 不調 | 出力がない・壊れた・時間切れ・認証の失敗は `UNAVAILABLE`。合格にも差し戻しにも数えない |
| 権限 | 接続を替えても権限は広げない。司法と要件の補助はツールなし |

今の接続：Claude Code（作業員・judge・憲法審査・要件の補助）、Codex（第2の司法・security）。交換できることと、能力・独立性を確かめたことは別。

### OS 接続

| 項目 | macOS（今） | WSL2（第一候補・未検証） | ネイティブ Windows |
|---|---|---|---|
| Z3 の分離 | `sandbox-exec`・Claude Code の sandbox | Claude Code の sandbox の Linux の実装（bubblewrap）が WSL2 で動くか、Z3 を読めないかを先に確かめる。**成り立たなければ実稼働を始めずに報告** | 別の到達点（今回は対象外） |
| ロック | `mkdir` | 同じ方式の候補（未検証） | — |

## 13. Codex の設計点検（第2版への指摘。11/7 23:5x）
