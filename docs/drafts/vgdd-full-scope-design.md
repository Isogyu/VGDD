## 1. 誰の、どんな課題か

- **今の実証の対象**：複数の開発 AI に作業を任せ、仕様の承認と統合の判断を1人で担う開発者（作者自身。この7日間の記録がある）
- **新しいペルソナ（仮説。未検証）**：業務の流れと正しい結果は説明できるが、コードの良し悪しは判断できない業務改善の担当者。提供の形は、IT の担当者が統治の環境を置き、業務の担当者が目的・条件・重要な変更・動作を確かめる
- 初心者が本当に使えるかは、開発の経験のない人に、答えを誘導せずに試してもらうまで「未検証」と書く

## 2. 実行の記録（昼夜共通の状態）

票の `status`（SPEC §5）は変えない。票とは別に、AI の呼び出し1回ごとの「実行の記録」を Z3 に持つ。

- 置き場所：`~/tsubuyaki-z3/runs/<run_id>.json`（Kernel だけが書く。開発エージェントは読めず書けない）
- `run_id`：呼び出しの種類・票・試行の番号・開始の時刻から作る一意の ID。同じ `run_id` の二度目の開始は拒む（重複の起動を防ぐ）
- 状態：

| 状態 | 入る経路 | 意味 |
|---|---|---|
| `reserved` | 共通の窓口（§3）が予算を予約した | まだ起動していない |
| `started` | 窓口が起動した | 動いている |
| `finished` | 呼び出しが終わり、利用量を読めた | 精算を待つ |
| `unknown` | 終わったが利用量を読めない・応答が壊れた・途中で落ちた | **予約を保ったまま**照合を待つ。0 として扱わない |
| `settled` | 窓口が実際の利用量で精算した | 終わり |
| `cancelled` | 起動の前に取り消した（停止・上限） | 予約を戻した |

- 再起動のとき、窓口は `started` のまま残った記録を `unknown` にし、予約を戻さない。オーナーの照合（`budget-reconcile.sh`、オーナーの操作）で精算する
- Kernel の停止（SPEC §8）は、開始済みの処理を強制終了しない。停止中、窓口は新しい `reserved` を作らない

## 3. 予算の予約と精算

### 単位

| 単位 | 中身 | 今の値（夜間） |
|---|---|---|
| トークン | 呼び出しごとの入力＋出力。Claude Code は `--output-format json` の `usage` から読む。Codex は出力の利用量の行から読む（読めなければ `unknown`） | 1票 2M、1晩 12M |
| 司法の回数 | judge・Codex judge・Codex security の呼び出し | 1晩 20 |
| 試行の回数 | 1票の作業員の試行（差し戻しの上限3回とは別に数える） | 未設定 |
| 時間 | 1回の呼び出しの上限時間と、運転の終わりの時刻 | 票ごとの `time_limit_min`、夜の終わり |
| 同時の数 | 同時に `started` でよい呼び出しの数 | 1（逐次） |

### 予約と精算

- 窓口は、開始の前に「その呼び出しが使いうる量の上限」を予約する。予約は台帳 `~/tsubuyaki-z3/budget/ledger.jsonl`（追記だけ、ハッシュチェーン）に書く。台帳の書き込みは排他（ロック）で1つずつ行い、**残高を読んでから書くまでの間に別の予約が入らない**ようにする
- 予約の量：トークンは「1票の上限 − その票のこれまでの使用量」と「全体の残り」の小さい方。残りが足りなければ起動を拒む
- 終わったら実際の利用量で精算し、予約との差を戻す。利用量を読めなければ `unknown` にし、予約は戻さない
- 上限の値は Z3 の `budget/limits.json` に置き、**オーナーの操作（`budget-set.sh`）だけ**で変える。AI による増額・回数の初期化・モデルの切り替えでの回避を認めない。再開しても、使用量と回数は台帳から数え直し、初期化しない

### 保証できること・できないこと

- この開発は Claude の**サブスクリプション（Max）**の利用枠で動いている。金額の上限は保証できない。保証できるのは「上限に達したら、次の起動を拒む」ことだけ（1回の呼び出しの途中で止める手段は、`--max-turns` と時間の上限しかない）
- API の従量課金に切り替える場合も、呼び出しの途中で費用を止める機能がなければ、厳密な金額の上限は保証できない。画面では「起動の制限」と書き、「費用の上限」とは書かない

### 管理の対象と、管理の外の経路

| 呼び出し | 今の起動のしかた | 窓口につなぐ方法 |
|---|---|---|
| 夜間の作業員 | `night-runner.sh` が `claude -p --agent worker` | `night-runner.sh` の起動の前後で窓口を通す |
| 司法（judge・Codex judge・security） | `gate-runner.sh` → `judge.sh`・`judge-codex.sh` | 同じ |
| 憲法審査 | `review-constitution.sh`（オーナー・立法補佐） | 同じ |
| **昼の作業員** | 行政の長が Claude Code の Agent ツールでサブエージェントを起動 | スクリプトを通らない。**PreToolUse フック（`policy.mjs`）で Agent ツールの呼び出しを予算の残りで判定**し、足りなければ拒む。利用量はサブエージェントの終わりに読めないので、台帳では「起動の回数」で数え、トークンは `unknown`（予約は1票の上限） |
| 行政の長・立法補佐のメインのセッション | 人が対話で動かす | **管理の外**。README と SPEC §12 に書く |
| 要件確認のアプリの呼び出し（§4） | アプリの Anthropic SDK | 窓口とは別。アプリの側で1回の上限と回数の上限を持ち、台帳には書かない（Z3 にアプリから書かない） |

## 4. 初心者向けの要件確認

- 画面 `/requirements`（ローカルだけ）で、段階ごとに質問する：課題 → 動作（入力・結果・例外）→ 制約（データ・外部送信・対象外）→ 確認（矛盾・不足）→ 承認の前の要約
- AI は推測で条件を決めない。AI の提案と本人の回答を分けて記録し、未解決の事項を出す。着手に欠かせない項目（目的・正しい結果の例・対象外）が空なら、下書きを作らない
- 出力は**票の下書きの文**（§1 目的・§2 受け入れ条件の候補・オーナーに聞くこと）。画面から `docs/tasks/` や Z3 には書かない。人が文を確かめ、立法補佐が票に整え、オーナーが今の `approve-spec.sh` で承認する（承認の窓口を増やさない）
- AI の呼び出しは、オーナーが決める（§9 の判断4）：Claude API を使う／LLM を使わず質問の型だけで進める。ローカル LLM は、言い換え・要約の下書きにだけ任意で使い、届かなければ省略する（クラウドへ自動で回さない）
- データは合成だけ。入力した文を保存しない（下書きの文は画面からコピーする）

## 5. 自動修正の共通化

- 今の夜間の流れ（差し戻し → 理由を渡して直す → 前検査 → 申請し直す）を使い、昼にも同じ規則を当てる
- 直してよいのは、同じ承認済みの §2 と `files_allowed` の中だけ。§2 の矛盾・依存の追加・禁止の操作が要るときは止めて人へ戻す（自動で承認しない）
- 司法は直さない。重大な不一致は今の裁定の規則のまま人へ戻す。夜間の held と release の条件は変えない
- 作業員に渡す差し戻しの理由は、判定のファイルの `findings` の要約だけ（今の夜間と同じ）。公開の画面と API には出さない
- 再開・重複：同じ票で `started` の実行の記録があれば、新しい試行を起動しない

## 6. 利用者の確認（受け入れ）

- 統合（`merged`）の後に、オーナーが動作を確かめて `accept.sh T-NNN`（オーナーの操作）で Z3 に「受け入れ」を記録する。統合と受け入れは別の出来事
- 公開の画面には「統合済み・受け入れ済み・受け入れ待ち」の件数と票の ID だけを出す

## 7. AI 接続と OS 接続の契約

### AI 接続（役割ごと）

| 項目 | 契約 |
|---|---|
| 入力 | 標準入力の文（役割ごとに決まった材料だけ。司法は差分・§2・監査の結果） |
| 出力 | 役割ごとの JSON のスキーマ（司法は `vgdd.verdict.v1`） |
| 利用量 | 読めれば `{input, output}` のトークン、読めなければ `null`（0 にしない） |
| 不調 | 出力がない・壊れた・時間切れ・認証の失敗は `UNAVAILABLE`。合格にも差し戻しにも数えない（今の SPEC §6-4〜6-6） |
| 権限 | 接続を替えても権限は広げない。司法はツールなし |

- 今の接続：Claude Code（作業員・judge・憲法審査）、Codex（第2の司法・security）。交換できることと、その接続の能力・独立性を確かめたことは別。新しい接続は、役割ごとに評価してから使う
- ローカル LLM は、司法・承認・統合・予算の増額には使わない

### OS 接続

| 項目 | macOS（今） | Windows（未検証） |
|---|---|---|
| 作業の場所と Z3 の分離 | `sandbox-exec` と Claude Code の sandbox | 未定。WSL2 の場合は Linux の sandbox の挙動を確かめる。ネイティブでは今のスクリプトの多く（bash・`sandbox-exec`）が動かない |
| 原子的な保存・ロック | `mkdir` のロック、`mv` | WSL2 は同じ。ネイティブは未定 |
| 検証の段階 | — | ①閲覧と起動 ②適合性テスト ③小さな票の承認から統合 ④負例（未承認・禁止の操作・停止・再開・予算・再試行）。通った段階だけを「確かめた」と書く |

## 8. 公開する集計

- Kernel の写し（`kernel-state.json`、厳しい形）に足す候補：予算の使用の割合（トークン・司法・試行。数と上限だけ）、実行の記録の状態ごとの件数（`unknown` を含む）、受け入れの件数。どれも件数と割合だけで、理由の本文・パス・ハッシュを入れない
- 形を変えるので法律の改正が要る（判例 ST1・ST8・ST10 の公開の規則を守る）

## 10. Codex の設計点検（11/7 23:3x、読み取りだけ）で直すこと

致命2・重大9・軽微2。票の起草の前に、この設計を次のとおり直す（未反映）。

| # | 指摘 | 直す方向 |
|---|---|---|
| 致命1 | 台帳と実行の記録の更新が1つの処理として確定しない。精算の前に落ちると二重に戻しうる | **台帳を唯一の正本**にし、実行の記録は台帳から作り直す。予約・取消・精算・照合を同じ排他と状態の検査の下に置き、各出来事に「何度送っても一度だけ効く ID」を持たせる。台帳の途中切れ・鎖の破損では新しい起動を拒む |
| 致命2 | 昼の Agent ツールの呼び出しを票に結び付けられない（入力に票の ID の欄がない。今の `policy.mjs` は Agent を許可している） | フックでの判定はやめ、**作業員の起動を Kernel の窓口に寄せる**：行政の長は起動の申請（票の ID だけ）を出し、Kernel が承認済みの票から指示を組み立てて `claude -p --agent worker` を起動する。フックは `worker`・`tester` の Agent ツールでの起動を拒む。昼の運転のしかたが変わるので、オーナーの判断が要る |
| 重大3 | 「使いうる量の上限を予約」は誤り。割り当てで、上限ではない | 「起動の判断のための予約」と書く。最小の起動量、実際の消費が予約を超えたときの記録と後続の停止を決める。トークンの厳密な上限も保証しないと明記 |
| 重大4 | 再起動のとき、古いプロセスが生きていても起動しうる。開始の時刻を含む ID では重複を防げない | 論理の要求の ID と実行の ID を分ける。「利用量が不明」と「生死が不明」を分け、生死が不明の間は同じ票を起動しない |
| 重大5 | 今のスクリプトは利用量を保存していない（`judge.sh`・`review-constitution.sh` は判定だけ取り出す。`judge-codex.sh` は `--json` を使わない） | CLI を直接囲む層で、判定とは別に利用量を保存する。Codex は `--json` の `turn.completed.usage`。キャッシュのトークンの扱い、不正な値の検査を決める |
| 重大6 | §0 に実装以上の説明：承認の指紋は §2 だけでなく front matter も含む。夜間のトークンは作業員の分だけで、読めないと 0 扱い。夜間の作業員は初回＋再試行1回。渡しているのは差し戻しの行で、`findings` の要約ではない | §0 を直す（今の夜間の「読めないと 0」は、この設計の「0 にしない」と食い違う既存の穴として書く） |
| 重大7 | 作業員に渡す理由の境界が足りない（自由文） | Kernel の側で、この票・この申請の判定から許した項目だけを取り出し、相対パス・長さ・秘密の検査を通す。不合格なら人へ戻す。指示ではなく診断の材料として渡す |
| 重大8 | アプリから Z3 に書かないことが権限として決まっていない | サーバーのプロセスの Z3 の読み書きの禁止、外部への公開の無効、入力・トークン・再試行の上限を決める。アプリの上限は Kernel の予算の外だと画面に出す |
| 重大9 | 期間・回数・同時の数の数え方が足りない（全体 12M は日か運転か累計か。票のない憲法審査の扱い） | 期間の ID、票のない呼び出しの区分、回数を消費する点、未精算の予約を含む残りを決める。同時の数は「起動を許してから終わりを確かめるまで」の枠で数える |
| 重大10 | 法律の改正の票を普通の作業員の票として扱うと統合できない（`vgdd/`・`.claude/` は保護パス）。写しの形を先に変えると今の画面が写し全体を拒む | 法律の差分は立法補佐が改正の手続きで、画面とアプリのコードは作業員の票で分ける。写しは読む側を先に両対応にしてから書く側を変える |
| 重大11 | 受け入れの記録が、確かめた成果物を特定しない | Z3 では票の ID・統合の SHA・承認の指紋・時刻に結び付ける。公開の写しには ID と件数だけ |
| 軽微12 | フックは sandbox の外で動くので Z3 を読める（今も STOP を読んでいる） | 根拠として書く。実機での確かめを検証の項目にする |
