## 1. 一文で

**新人のつまずきを、組織の知識に変える。**

補助の一文：つぶやくだけで、あなたの試行錯誤がチームの知恵になる。共有するかどうかは、あなたが決める。

新人が作業中に書いた短いメモ（つぶやき）から、つまずき・試したこと・解決・判断の理由を整理し、手順書の原案と「判断のポイント」（暗黙知）を、本人の確認を経てチームに引き継げる形にする。テーマ1「あなたにしかない深さを。」に応募する。

## 2. 題材と原体験 [初版]

### 2.1 原体験（オーナー、新卒1年目 SE）

新しいタスクを任されたが、何をすればよいか十分に理解できなかった。AI と壁打ちしながら自力で紐解こうとしたが、AI が整理した解釈が正しいか確信が持てず、「見当違いの質問をしたらどうしよう」という不安で人に聞けなかった。既存コードの保存場所のように、AI では確実に分からないことを人に確認するまでに**半日**かかった。勤務地が他のメンバーと異なり、連絡手段はチャットとオンライン会議が中心だった。

振り返り：**30分の時点なら聞けた。時間が経つほど聞きにくくなった。** 問題は「質問文が書けない」ことではなく、「自分が何を理解していないかを整理できず、AI の推測と確認済みの事実を区別できなかった」ことにあった。

### 2.2 原体験から導く、アプリが示す価値（審査「インパクト30%」の根拠）

1. **記録の負担を増やさない。** 作業中のつぶやきがそのまま入力になる。日報や手順書を別に書かせない。
2. **AI の推測と事実を区別して見せる。** AI 整理（M4）と手順書（M5）では、元のメモを根拠として示し、根拠のない部分は「AI の推測」と表示する。これは公式注記 DC-009「事実確認が不明確なもの」への答えでもある。
3. **本人が共有するかを決める。** 共有候補は機密検査（M6）と本人確認（M9）を通る。人事評価への流用を避ける注意書きを置く。
4. **先輩の判断の理由を残す。** 先輩の記録から「判断のポイント」を抽出し、新人の記録から作った手順書に添える（M5）。

**差別化の3点（D-32。最も近い既存作品は、熟練者の勘を形式知にする系。README とデモで明示する）**

| # | 本作 | 近い作品・一般の AI チャットとの違い |
|---|---|---|
| 1 | **新人のつまずきから**知識を作る | 熟練者に聞いて書き起こすのではなく、新人が作業中に残したメモが出発点。先輩の判断の理由は、新人の手順書に添える形で入る |
| 2 | **AI の推測と事実を分けて**見せる | 整理・手順書の各項目に根拠のメモを付け、根拠がない項目は「AI の推測」と表示する。足りない情報は本人に追加の質問で埋める（M4-5） |
| 3 | **共有するかを本人が決める** | 機密検査と抽象化の案を見たうえで、本人が承認・編集・却下する。承認前の内容はチームに出ない |

### 2.3 合成データへの写し方

原体験は**架空の会社・プロジェクト・人物・作業内容に置き換えて**使う。実在の会社名・プロジェクト名・人名・顧客名・勤務地は、リポジトリ・合成データ・README・動画のどこにも入れない。実案件の作業名や、技術の固有の組み合わせも書かない。原体験の「依頼の意図と成果物の条件が分からず、AI では分からないことを人に聞くまでに半日かかった」という**構造だけ**を残す。

| # | 作業名 | 新人のつまずき（合成ログの筋） | 先輩の判断の理由（例） |

## 4. 画面と流れ [初版]

画面は最小限の4つ。

| 画面 | 役割 | 関係する機能 |
|---|---|---|
| S-1 作業画面 | 入力欄1つ。作業開始・メモ・作業終了をここで行う。右側に現在の作業と経過時間、「いまの理解を整理」ボタン | M1・M2・M3・M10 |
| S-2 整理結果 | 作業終了後の AI 整理と、根拠になった元のメモ | M4 |
| S-3 共有候補の確認 | 機密検査の結果と抽象化の案、承認・編集して承認・却下 | M6・M9 |
| S-4 チームの知恵 | 承認済みの知識と、手順書の原案＋判断のポイント | M5・C2・S1 |

ユーザーの切り替えは画面上部のセレクタ（新人A／新人B／先輩C）。ログイン・認証は作らない。

## 5. 受け入れ基準（必須 M1〜M9） [初版・承認対象]

各基準は「検証方法」で確認できる形にする。評価用テストのコードは 11/7 にオーナーが書く。

### M1 作業開始

| # | 受け入れ基準 | 検証方法 |
|---|---|---|
| M1-1 | 入力欄に「〇〇の作業開始」と入力するか、作業名を入れて「開始」ボタンを押すと、作業セッションが1つ作られ、作業名と開始時刻が画面に表示される | 入力1回でセッションが1件できる |
| M1-2 | 開始の認識は決定論的な照合（末尾が「の作業開始」「開始」等）で行い、LLM 判定に頼らない | 同じ入力は常に同じ結果になる |
| M1-3 | 進行中の作業がある状態で別の作業を開始すると、確認を求める（並行作業は MVP では1本） | 2本目の開始で確認表示が出る |
| M1-4 **[質問3で合意した最小形、D-33②で拡張]** | 同じ作業名の記録があれば、開始直後に次を1〜2行ずつ表示する：①自分の過去の記録の「つまずき」（元のメモの日時つき）②**チームの承認済み知識**（M9 で承認されたもの。記録者の表示名つき）。意味検索はしない（作業名の完全一致） | W1 の2回目の開始で①が出る。新人B が W1 を開始すると、新人A の承認済み知識が②として出る |

### M2 作業中のメモ

| # | 受け入れ基準 | 検証方法 |
|---|---|---|
| M2-1 | 進行中の作業に対して短文のメモを追加でき、各メモに時刻が付く | 時刻がメモごとに表示される |
| M2-2 | 連続して5件書いても、順序と時刻が保たれる | 5件入力後、表示順と保存順が一致する |
| M2-3 | メモは保存のたびに機密検査（M6-1）を通り、該当があれば送信前に警告する | 罠の入力で警告が出る |

### M3 作業終了と所要時間

| # | 受け入れ基準 | 検証方法 |
|---|---|---|
| M3-1 | 「作業終了」と入力するかボタンを押すと、終了時刻と所要時間（分）が記録・表示される | 終了後に分数が表示される |
| M3-2 | 終了後に自動で M4 の AI 整理を開始し、進行中であることを画面に示す | 終了直後に整理中の表示が出る |

### M4 AI 整理（固定スキーマ）

| # | 受け入れ基準 | 検証方法 |
|---|---|---|
| M4-1 | 作業1本のメモ全体を Claude API（Sonnet 5.5）に送り、固定スキーマの JSON を得る。項目：**つまずき／原因／試したこと／解決／判断の理由／学び／未解決／人に確認すべきこと**（最後の1項目は採用した提案 P-2。AI の利用可能な情報では確実に答えられない事項） | 合成ログ3本（W1〜W3）で8項目すべてが埋まる。該当なしは「なし」と明示。W1 で「既存コードの場所」が「人に確認すべきこと」に出る |
| M4-2 | 各項目に**根拠となった元のメモの ID** を付ける。根拠がない項目は「AI の推測」と表示する | 画面で各項目から元のメモにたどれる。推測の表示が出る |
| M4-3 | スキーマ違反（必須項目の欠落、未知の項目、根拠 ID の不一致）を検出して再試行する。2回失敗したら「整理できませんでした」とメモの原文を表示する | 壊れた応答を模した入力で検出が動く |
| M4-4 | API キーが設定されていないときは、保存済みの AI 出力（デモ用）を表示する**デモモード**で動く | キーなしで W1〜W3 の整理結果が表示される |
| M4-5 **[D-33①]** | 整理の結果、情報が足りない項目があれば、AI が本人に**追加の質問を1〜2問**返す（固定スキーマの `questions` 配列。例：「解決した」→「最初に何を確認しましたか？」）。本人が答えると、答えをメモとして保存し、整理をやり直して反映する。質問は2問まで、やり直しは1回まで | W1 の合成ログで質問が1問以上出る。答えると該当項目が埋まり、根拠に答えのメモ ID が付く |

### M5 手順書の原案と判断のポイント

| # | 受け入れ基準 | 検証方法 |
|---|---|---|
| M5-1 | 同じ作業名の記録2件以上から、手順書の原案（番号付きの手順）を生成する。1件しかなければ「記録が不足」と表示する | W1 の新人A＋先輩C の記録で原案が出る |
| M5-2 | 手順書とは別に「判断のポイント」欄を置き、先輩の記録から「なぜそうするか」を抽出する | W1 で先輩C の判断の理由が欄に出る |
| M5-3 | 手順と判断のポイントの各項目に、根拠となった元のメモ（記録者・日時）を表示する。根拠のない項目は「AI の推測」と表示する | 画面で各項目から元のメモにたどれる |
| M5-4 | 画面上に「原案。利用前に本人・先輩の確認が必要」と常に表示する | 表示を確認 |

### M6 機密情報の検査

| # | 受け入れ基準 | 検証方法 |
|---|---|---|
| M6-1 | **決定論的な検出**：メールアドレス、電話番号、カード番号らしい数字列（Luhn 検査）、API キーの形式（`sk-`・`AKIA` 等の接頭辞と長さ）、**登録した語句（顧客名・プロジェクト名のリスト）との照合**。メモ保存時と共有候補の作成時に動く | 罠の入力5件すべてで警告が出る（5件目は登録語句の照合で顧客名を検出） |
| M6-2 | 共有候補に対しては、決定論的な検出に加えて Claude API に「登録されていない顧客名・金額・未公開の計画」の候補を挙げさせる。AI は**検出を足すだけ**で、決定論的な検出結果を取り消せない | 罠5件目で、登録語句の照合（顧客名）に加えて AI が金額を検出候補に足す |
| M6-3 | 検出箇所ごとに**抽象化の案**（例：「株式会社〇〇」→「顧客A社」、金額→「数百万円規模」）を示し、元の文との違いを並べて表示する。採否は本人が選ぶ。自動では置き換えない | 検出箇所に案が表示され、選択できる |
| M6-4 | 「パターンで取りこぼす情報がある。完全な匿名化はできない」という注意を画面と README に書く | 表示を確認 |

### M9 共有前の本人確認

| # | 受け入れ基準 | 検証方法 |
|---|---|---|
| M9-1 | 共有候補（M4 の整理結果から作った要約。原文のメモは含まない）に対し、**そのまま承認／編集して承認／却下**の3操作ができる | 3操作がすべて動く |
| M9-2 | 承認の記録（日時、操作、承認後の本文、却下理由は任意）を保存し、本人が後から見られる | 記録画面で確認できる |
| M9-3 | 承認されていない内容は、チームの知恵（S-4）に出ない | 却下した候補が S-4 に出ない |
| M9-4 | 承認画面に「共有内容は人事評価に使わない」旨の注意書きを置く | 表示を確認 |
| M9-5 | 本人は承認済みの共有を取り下げられる | 取り下げ後に S-4 から消える |

### M10 いまの理解を整理と質問文の下書き（採用した提案 P-1'・P-3）

| # | 受け入れ基準 | 検証方法 |
|---|---|---|
| M10-1 | 進行中の作業で「いまの理解を整理」ボタンを押すと、それまでのメモに M4 と同じ整理を実行し、結果を S-1 に差し込んで表示する。項目は「確認済みの事実／AI の推測／未確認／人に確認すべきこと」の見出しで並べ替えて見せる。情報が足りなければ M4-5 と同じ追加の質問を1〜2問返す。作業は終了しない。タイマーによる自動実行はしない | W1 のメモ3件の時点でボタンを押すと、整理結果と追加の質問が表示され、作業が進行中のまま残る |
| M10-2 | M4 または M10-1 の「人に確認すべきこと」から、先輩への質問文を1クリックで下書きする。構成：担当作業／いま理解していること／試したこと／未確認のこと／聞きたいこと。コピーボタンを置く。送信機能は作らない | W1 で下書きが5つの構成で生成され、コピーできる |
| M10-3 | 下書きにも M6-1 の機密検査がかかり、該当があれば警告する | 顧客名を含むメモから下書きすると警告が出る |

### M7 合成データでのデモ

| # | 受け入れ基準 | 検証方法 |
|---|---|---|
| M7-1 | §3 の合成データ（作業5本、罠5件）を生成スクリプトか JSON の元データとしてリポジトリに置く。DB ファイルはコミットしない | `npm run seed` 相当で投入できる |
| M7-2 | デモの筋書き（§7）を3分以内で通せる | 録画前に通し練習で計測 |
| M7-3 **[D-32③]** | **罠セットでの計測**：合成データの罠5件＋通常のメモに対する M6 の検出率（見逃し・誤検出の件数）と、合成ログ3本に対する M4 のスキーマ充足率を測る。プロンプトや検出規則を改善した前後で測り、README に数字で載せる | 計測スクリプトが件数を出力し、改善前後の2回分が README にある |
| M7-4 **[D-33③]** | **比較評価**：合成ログ10件（W1〜W3 を増やす）と、オーナーが作る正解ラベル（項目ごとの期待値。`~/tsubuyaki-z3/` に置き、開発エージェントは読めない）で、「単なる要約」（項目指定なしのプロンプト）と「本作の整理（固定スキーマ＋根拠＋追加の質問）」を比べる。指標：項目の充足率、根拠 ID の正しさ、「人に確認すべきこと」の一致。結果は README に表で載せる。件数が少ないため統計的な主張はしない | オーナーが評価を実行し、10件分の表が README にある |

### M8 審査員が触れる README

| # | 受け入れ基準 | 検証方法 |
|---|---|---|

## 8. 将来構想（README と動画の最後で説明。期間中は作らない） [初版]

質問1・2・5 の構想のうち、D-22 の範囲外のもの。禁止例（基本的な RAG アプリ、汎用チャット）に近づかないよう、説明だけにする。

- 階層フォルダによる複数作業チャットの並行管理

- 過去の知見の意味検索（ベクトル DB）と会話内での自然な再提示
- 統合 AI による複数チャット・複数メンバーの横断分析、潜在課題の発見
- 作業開始からの経過時間に応じた自動分析（30分チェックインのタイマー版）と通知の強度制御。MVP では本人がボタンで呼び出す形（M10-1）だけを作る。タイマー版は `docs/ideas.md` に残した
- 作業時間の半自動計測（中断・切り替えの推定）
- 改善タスクの生成・実行支援・効果検証（KPI）
- 役割別の閲覧権限、管理者の承認、個人が特定されない形での組織分析、感情・不安の組織傾向の分析
- ローカル LLM への差し替え、Slack・Teams 等との連携
- 心理的な課題の扱い：個人別の感情評価はしない（オーナーの決定 No.14）
