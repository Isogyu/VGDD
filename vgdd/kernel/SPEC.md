# VGDD Governance Kernel 規範仕様（Kernel p0.4.2）

- 作成：2026-11-05（開催期間中に新規作成）
- 位置づけ：VGDD の統治を強制する部分（Governance Kernel）の**規範**。言語やモデルに依存しない形で書く。このリポジトリの `vgdd/hooks/`・`vgdd/scripts/` は**参照実装**で、`vgdd/conformance/run.mjs` が規範との一致を試す（ADR-023・ADR-034 の前提）
- 語の強さ：**しなければならない（MUST）**／**してはならない（MUST NOT）**／**するべき（SHOULD）**。MUST に反する実装は適合しない
- 機械が読む部分：`vgdd/kernel/capabilities.json`（役割と権限の表）、`vgdd/schemas/kernel-decision.schema.json`（判定の記録）。この文書と食い違えば、機械が読む部分を正とし、この文書を直す

## 1. Kernel とは何か、何でないか

1. Kernel は、**あらかじめ決めた権限・規則・承認の条件を強制する信頼基盤**である。判断する主体ではない。Kernel は LLM を使って可否を決めてはならない（MUST NOT）。判定（合否）は司法が出し、Kernel はその判定の**扱い**（統合する・しない）を機械的に決める
2. Kernel は第4の権力ではない。Kernel を変えられるのは主権者（オーナー）だけで、その変更は立法の手続き（起草 → 憲法審査 → オーナーの承認）を経る（ADR-011）
3. 役割の境界は、プロンプトでなく実行環境で強制しなければならない（MUST。ADR-001）。強制の層：権限ルール（permission）、フック（hook：Policy Decision Point）、OS の sandbox、worktree isolation、別プロセス・別権限（process）、裁判所の検査（gate）、Z3 の承認の記録（ledger）、事後検知（detect）。**約束だけで強制のないもの（promise）は、権限の表に promise と書いて公開しなければならない**（MUST）

## 2. 役割と識別

| 役割 | 識別の根拠 | 主な権限 |
|---|---|---|
| 主権者（owner） | 人。Kernel の外 | 仕様の承認、統合の承認（朝）、裁定、停止・再開、法律の制定 |
| 立法（legislative_assistant ほか） | 別のアカウント | 法律・仕様の**起草**。効力は持たない |
| 行政の長（executive_head） | フック入力の `agent_type` が空、cwd が main の checkout | 票の起草、作業員の起動、統合の申請 |
| 作業員・テスト担当（worker・tester） | `agent_type`、cwd が `.claude/worktrees/<name>` | 自分の worktree の中だけを書く |
| 司法（judge・codex_judge・constitutional_review） | ツールのない起動（`disallowedTools`、読み取り専用の sandbox） | 判定を返す。書かない |
| 裁判所の執行（gate_runner）・夜間の代行（night_runner） | オーナーの権限で sandbox の外のプロセス | 統合（gate_runner だけ）、票の status と記録 |

- AI の役割は、フックの入力（`agent_type`・`cwd`）と、起動の仕方（どの定義・どの権限で起こしたか）で識別する。**git の作者名は識別の根拠にしてはならない**（MUST NOT。作者名は誰でも名乗れる。`run.mjs --observe` は作者名を観測として数えるだけ）
- 役割ごとの権限の全体は `capabilities.json`。各権限に `allowed`（できる役割）、`enforced_by`（止める層）、`probes`（適合性テストがフックに入れる操作）、`expect`（フックの判定）、`known_gaps`（強制の穴）を書く

## 3. 操作の要求と判定（Policy Decision Point）

1. エージェントのすべてのツール呼び出しは、実行の前に Kernel の判定を受けなければならない（MUST）。判定は `allow` か `deny` で、理由を必ず持つ
2. 判定は、実行の前に証拠ストアへ1行記録しなければならない（MUST）。**記録できなければ拒否する**（fail-closed）。フック自体が動かないときも、すべての操作を止める（`onFailure: block`）
3. 記録の形は `kernel-decision.schema.json`：誰が（`agent_type`・`cwd`・`session_id`・`git_branch`）、何を（`operation`・`target`）、どう判定し（`decision`）、なぜか（`reason`）、前の行の指紋（`prev_hash`）
4. 実行の結果（成功・失敗・分類器の拒否）は別の行（`type: outcome`）で `tool_use_id` により結ぶ。**allow の判定に outcome がない行**は、権限ルールの拒否か未完了であり、数えて公開する

## 4. 仕様の統治（Approval Gate。成立条件②、ADR-005）

1. **仕様**とは、票の front matter のうち運用の項目（`status`・`branch`・`worker`）を除く**すべての行**と、本文の「受け入れ条件（完了条件）」の節、`requirements_source` が票でなければ `docs/requirements.md` の該当 ID の行である。項目を選んで正規化してはならない（MUST NOT。選ばなかった書き方、たとえば重複キーが、指紋を変えずに裁判所の読み取りだけを変える穴になる）。運用の項目と §6 の記録は仕様ではない
2. 仕様の**指紋**は、上の部分を決まった順に並べた文字列の SHA-256（`vgdd.spec.v2`。参照実装 `spec-digest.mjs`）。仕様は main にコミットされた票から読み、作業ツリーや作業ブランチの票を使ってはならない（MUST NOT）。**裁判所と夜間の代行が統治の項目（`files_allowed`・`requirements`・`security_review`）を読むときも、main にコミットされた票から読まなければならない**（MUST。承認した仕様と、実際に効く仕様を同じにする）
3. 仕様を起草するのは誰でもよい。**効力は、オーナーがその指紋を承認した記録（Z3 の `spec_approvals.jsonl`、`approved_by: owner`）だけが与える**。承認の記録は行政が書けない場所に置かなければならない（MUST）
4. 裁判所は、main の票の今の指紋に承認がない申請を、**司法を呼ぶ前に** `blocked` にしなければならない（MUST）。夜間の代行は、承認のない票を作業員に渡してはならない（MUST NOT）
5. 承認の後に仕様が1文字でも変われば、承認は効かない（指紋が変わるため）。承認し直す

## 5. 票の状態

| 状態 | 入る経路（誰が） | 意味 |
|---|---|---|
| `ready` | 起草（行政の長・立法補佐）。オーナーの承認で効力 | 着手してよい |
| `in_progress` | 行政の長・夜間の代行（着手）、裁判所（差し戻し） | 作業中 |
| `review` | 行政の長・夜間の代行（申請の前） | 統合の申請中 |
| `review`＋held | 裁判所（夜間に合格。`held.jsonl`） | 朝のオーナーの承認待ち |
| `merged` | 裁判所（昼）、release（朝、オーナー） | main に入った |
| `blocked` | 裁判所（保護パス・仕様の未承認・判定の重大な不一致・差し戻しの上限など） | オーナーの判断待ち |

- `merged` に変えてよいのは裁判所と release だけ（MUST）。裁判所が記録としてコミットしてよいのは、その周回に自分で書き換えた票と `_board.json` だけ（MUST。ほかの誰かのコミットしていない変更を裁判所の名前で main に入れない。OBS-044）。書き換える票にほかの誰かのコミットしていない変更が残っていれば、**作業ツリーの票をコミットしてはならない**（MUST NOT。書けば他人の書きかけが裁判所の名前で main に入る。OBS-050）。裁判所は、申請中の票にほかの誰かの書きかけがある間は**その申請を処理しない**（MUST。判定も記録も統合もせず、申請を残して `ticket_dirty_wait` を記録する。確かめるのは処理の始めと、held の記録・統合の直前。p0.4.2）。書きかけがコミットされるか戻されれば、次の周回で普通に処理する。限界：書きかけがないことを確かめてから記録のコミットまでの数秒の間に人が票を書けば、それは記録のコミットに入る（人と裁判所が同じ checkout を使う限り残る。運用で、裁判所が動いている間は票を直さない）差し戻しの上限は3回（取り消された差し戻しは数えない）

## 6. 司法の独立（成立条件③）

1. 司法の入力は、裁判所が機械的に集めた**差分・main の票の受け入れ条件（または要件の行）・決定論的な監査の結果**だけでなければならない（MUST）。行政の説明（コミットの本文、票の手順の案・記録、作業員の報告、会話）を入れてはならない（MUST NOT）
2. 司法はツールを持ってはならない（MUST NOT）。別系統のモデルの司法（Codex）は、同じ入力の組み立てを使う（SHOULD）
3. 決定論的な監査の不合格・未実行は、LLM の合格で取り消せない（MUST）
4. 二つの司法の判定が重大な指摘で分かれたら、統合せずにオーナーの裁定を待つ（MUST）。裁定は票と申請の SHA に結び付ける

## 7. 統合（成立条件④）

1. main に統合できるのは裁判所（gate_runner）と、朝のオーナーの承認（release）だけ（MUST）。行政は `git merge`・main の参照の書き換え・main への push ができてはならない。**行政の長が main に直接コミットしてよいのは `docs/` の下（票・記録・文書）だけ**（MUST。ソースは作業員のブランチから裁判所を通す。`-a`・パスの指定・`--amend`・作者名を変える `-c` は main では拒否）。作業員は main にコミットできない
2. 裁判所は、申請ごとに最初に取った main の完全な SHA に、仕様の照合・差分・候補・司法・統合のすべてを固定しなければならない（MUST。確認と使用の時刻の差を作らない）。検査した候補のコミット（その SHA ＋ 申請の SHA）だけを fast-forward で統合する。held の記録と統合の直前に、停止と main の前進を確かめ直し、main が進んでいれば検査し直す
3. 差分が保護パス（法律・憲法・CI・票の盤・申請）か `files_allowed` の外に及べば統合しない
4. 夜間（`--hold`）は合格しても統合しない。朝に release が、今の main と組み直した変更が夜に判定した変更と一字一句同じことを確かめてから統合する。release は錠で直列化し（MUST。片方の取り消しがもう片方の統合を消さない）、申請がすでに main に入っていれば何もしない。取り消しは、HEAD がその実行の作った統合のコミットのときだけ行う。統合したら票の status を merged にして、その票だけをコミットする（p0.4.1、OBS-048）

## 8. 停止と復旧（ADR-010・ADR-027）

1. オーナーは Kernel 全体を止められなければならない（MUST）。停止は Z3 の `STOP`（エージェントは作れず消せない）
2. 停止中、Kernel は読み取りのツール（ファイルを読む・探す）以外のすべての操作を拒否しなければならない（MUST）。**Bash はすべて拒否する**（文字列の照合では、読み取りに見えて書き込むコマンドを見分けきれない）。裁判所は申請を処理せず（周回の始め・申請ごと・held の記録と統合の直前に確かめる）、夜間の代行は票を取らず、release（票ごと）と仕様の承認は動かない
2b. 停止は、停止の後に始まる操作を止める。**停止の前に始まって実行中の処理（長い Bash、夜間の作業員、司法の呼び出し）を強制終了はしない**（既知の限界。それらの次のツール呼び出しはフックが止める）
3. 再開の前に、少なくとも次を確かめなければならない（MUST）：証拠ストアのハッシュチェーンとチェックポイント、共有の git の設定が基準値と同じ、main の checkout が main ブランチにあり未コミットの変更も未追跡のファイルもない、停止の時点の main（STOP に書いた完全な SHA）が今の main の祖先である、停止の後に main に入ったコミットがない（**作者名にかかわらず**、あればオーナーが一覧を確かめて明示的に受け入れる）。どれかを確かめられなければ再開しない
4. 停止と再開は錠で直列化する。再開の記録を先に書き、その後で STOP を消さずに移す（記録に失敗すれば再開しない）

## 9. 予算（ADR-018・ADR-020）

- 夜間の代行は、並行数（**既定は1＝逐次**）・1晩の票数・時刻・1票と1晩のトークン・司法の呼び出し回数・空き容量の上限を持ち、上限に達したら新しい票を取らない（MUST）。Max の5時間枠の残量は読めないため、利用上限の文言で止める

## 10. 証跡（成立条件⑤、ADR-009）

- 証拠ストアは追記だけで、各行が前の行の SHA-256 を持つ（ハッシュチェーン）。裁判所は周回ごとに件数と末尾の行の指紋をチェックポイントとして残し、末尾の切り詰めを検出する
- 判定（司法）、承認（仕様・裁定・朝の統合）、停止・再開、外部の前進の検知は、Z3 の記録に残す（`verdicts/`、`spec_approvals.jsonl`、`rulings.jsonl`、`held.jsonl`、`gate_events.jsonl`）
- 限界：同じ機械の管理者（オーナーの権限）は記録を書き換えられる。外部への固定（アンカー）はしていない

## 11. 適合性（ADR-012・ADR-025）

- 適合性テストは `vgdd/conformance/run.mjs`。群と成立条件の対応：C1（役割分離と権限）→①④、C2（仕様の統治）→②、C3（独立司法）→③、G（裁判所の場面）→②④、H（行政の長の main へのコミット）→④、K（停止と再開）、N（夜間の代行）、A（証跡）→⑤、M（権限の表の自己検査：どの権限にも確かめ方があり、参照した試験が合格している）
- テストは、止めるべき操作が止まることと、**通すべき操作が通ること（陽性の対照）**の両方を試さなければならない（MUST）。前の版の実装に対して実行し、新しい規則の試験が実際に落ちることを確かめる（試験が空回りしていないことの確認）
- 「VGDD Core に適合」とは名乗らない。名乗れるのは「この構成で、適合性テスト N 件に合格（実装と日時）」だけ。権限の表の promise と known_gaps は適合の主張に含めない

## 12. 保証できないこと

- フックの Bash の判定は文字列照合で、回避の余地がある（書き込みは OS の sandbox が最後に止める）
- 人が承認画面で許可した操作は止められない（記録は残る）
- 裁判所の周回ごとの事後検知（`main_advanced_outside_gate`）は、作者名が `gate-runner` のコミットを除いて数える。作者名は偽れる。行政の長が作者名を変えるコミットはフックが main で拒否するが、フックの Bash の判定は文字列照合で、回避の余地は残る（再開の確認は作者名を使わない）
- 行政の長が main の checkout でソースを**書く**こと自体は止めていない（コミットできるのは docs/ の下だけ。書いたソースは裁判所を通らない限り main に入らない）。票の §2 を起草すること自体も止めていない（効力は §4 の承認で縛る）
- 司法の判定の正しさ（LLM）は保証しない。二つの系統の司法が同じ見落としをする可能性は残る
- 同じ機械の管理者権限を持つ者に対する完全な防御と、記録の不変性は保証しない
