# VGDD Governance Kernel 規範仕様（Kernel p0.4.10）

- 作成：2026-11-05（開催期間中に新規作成）
- 位置づけ：VGDD の統治を強制する部分（Governance Kernel）の**規範**。言語やモデルに依存しない形で書く。このリポジトリの `vgdd/hooks/`・`vgdd/scripts/` は**参照実装**で、`vgdd/conformance/run.mjs` が規範との一致を試す（ADR-023・ADR-034 の前提）
- 語の強さ：**しなければならない（MUST）**／**してはならない（MUST NOT）**／**するべき（SHOULD）**。MUST に反する実装は適合しない
- 機械が読む部分：`vgdd/kernel/capabilities.json`（役割と権限の表）、`vgdd/schemas/kernel-decision.schema.json`（判定の記録）。この文書と食い違えば、機械が読む部分を正とし、この文書を直す

## 1. Kernel とは何か、何でないか

1. Kernel は、**あらかじめ決めた権限・規則・承認の条件を強制する信頼基盤**である。判断する主体ではない。Kernel は LLM を使って可否を決めてはならない（MUST NOT）。判定（合否）は司法が出し、Kernel はその判定の**扱い**（統合する・しない）を機械的に決める
2. Kernel は第4の権力ではない。Kernel を変えられるのは主権者（オーナー）だけで、その変更は立法の手続き（起草 → 憲法審査 → オーナーの承認）を経る（ADR-011）
3. 役割の境界は、プロンプトでなく実行環境で強制しなければならない（MUST。ADR-001）。強制の層：権限ルール（permission）、フック（hook：Policy Decision Point）、OS の sandbox、worktree isolation、別プロセス・別権限（process）、裁判所の検査（gate）、Z3 の承認の記録（ledger）、事後検知（detect）。**約束だけで強制のないもの（promise）は、権限の表に promise と書いて公開しなければならない**（MUST）

## 2. 役割と識別

| 役割 | 識別の根拠 | 主な権限 |
|---|---|---|
| 主権者（owner） | 人。Kernel の外 | 仕様の承認、統合の承認（朝）、裁定、停止・再開、法律の制定 |
| 立法（legislative_assistant ほか） | 別のアカウント | 法律・仕様の**起草**。効力は持たない |
| 行政の長（executive_head） | フック入力の `agent_type` が空、cwd が main の checkout | 票の起草、作業員の起動、統合の申請 |
| 作業員・テスト担当（worker・tester） | `agent_type`、cwd が `.claude/worktrees/<name>` | 自分の worktree の中だけを書く |
| 司法（judge・codex_judge・constitutional_review） | ツールのない起動（`disallowedTools`、読み取り専用の sandbox） | 判定を返す。書かない |
| 裁判所の執行（gate_runner）・夜間の代行（night_runner） | オーナーの権限で sandbox の外のプロセス | 統合（gate_runner だけ）、票の status と記録 |

- AI の役割は、フックの入力（`agent_type`・`cwd`）と、起動の仕方（どの定義・どの権限で起こしたか）で識別する。**git の作者名は識別の根拠にしてはならない**（MUST NOT。作者名は誰でも名乗れる。`run.mjs --observe` は作者名を観測として数えるだけ）
- 役割ごとの権限の全体は `capabilities.json`。各権限に `allowed`（できる役割）、`enforced_by`（止める層）、`probes`（適合性テストがフックに入れる操作）、`expect`（フックの判定）、`known_gaps`（強制の穴）を書く

## 3. 操作の要求と判定（Policy Decision Point）

1. エージェントのすべてのツール呼び出しは、実行の前に Kernel の判定を受けなければならない（MUST）。判定は `allow` か `deny` で、理由を必ず持つ
2. 判定は、実行の前に証拠ストアへ1行記録しなければならない（MUST）。**記録できなければ拒否する**（fail-closed）。フック自体が動かないときも、すべての操作を止める（`onFailure: block`）
3. 記録の形は `kernel-decision.schema.json`：誰が（`agent_type`・`cwd`・`session_id`・`git_branch`）、何を（`operation`・`target`）、どう判定し（`decision`）、なぜか（`reason`）、前の行の指紋（`prev_hash`）
4. 実行の結果（成功・失敗・分類器の拒否）は別の行（`type: outcome`）で `tool_use_id` により結ぶ。**allow の判定に outcome がない行**は、権限ルールの拒否か未完了であり、数えて公開する

## 4. 仕様の統治（Approval Gate。成立条件②、ADR-005）

1. **仕様**とは、票の front matter のうち運用の項目（`status`・`branch`・`worker`）を除く**すべての行**と、本文の「受け入れ条件（完了条件）」の節、`requirements_source` が票でなければ `docs/requirements.md` の該当 ID の行である。項目を選んで正規化してはならない（MUST NOT。選ばなかった書き方、たとえば重複キーが、指紋を変えずに裁判所の読み取りだけを変える穴になる）。運用の項目と §6 の記録は仕様ではない
2. 仕様の**指紋**は、上の部分を決まった順に並べた文字列の SHA-256（`vgdd.spec.v2`。参照実装 `spec-digest.mjs`）。仕様は main にコミットされた票から読み、作業ツリーや作業ブランチの票を使ってはならない（MUST NOT）。**裁判所と夜間の代行が統治の項目（`files_allowed`・`requirements`・`security_review`）を読むときも、main にコミットされた票から読まなければならない**（MUST。承認した仕様と、実際に効く仕様を同じにする）
3. 仕様を起草するのは誰でもよい。**効力は、オーナーがその指紋を承認した記録（Z3 の `spec_approvals.jsonl`、`approved_by: owner`）だけが与える**。承認の記録は行政が書けない場所に置かなければならない（MUST）
4. 裁判所は、main の票の今の指紋に承認がない申請を、**司法を呼ぶ前に** `blocked` にしなければならない（MUST）。夜間の代行は、承認のない票を作業員に渡してはならない（MUST NOT）
5. 承認の後に仕様が1文字でも変われば、承認は効かない（指紋が変わるため）。承認し直す
6. 承認は**法律の系統**にも結び付く（MUST。p0.4.4、INV-06・ADR-038）。承認の記録は、承認した時点の main の `kernel_version` の先頭（例 `p0.4`）を `policy_line` に持つ。法律の権限の表のある ref では、照合は `policy_line` が同じ ref の系統と一致する承認だけを有効とする。権限の表があるのに読めない・版の形が違う ref では、どの承認も効かない（MUST。fail-closed）。権限の表のない ref（法律を持たないリポジトリ）では系統を結び付けない。法律の系統が変われば承認し直す（同じ系統の中の版の上がり（p0.4.3 → p0.4.4）では外れない）

## 5. 票の状態

| 状態 | 入る経路（誰が） | 意味 |
|---|---|---|
| `ready` | 起草（行政の長・立法補佐）。オーナーの承認で効力 | 着手してよい |
| `in_progress` | 行政の長・夜間の代行（着手）、裁判所（差し戻し） | 作業中 |
| `review` | 行政の長・夜間の代行（申請の前） | 統合の申請中 |
| `review`＋held | 裁判所（夜間に合格。`held.jsonl`） | 朝のオーナーの承認待ち |
| `merged` | 裁判所（昼）、release（朝、オーナー） | main に入った |
| `blocked` | 裁判所（保護パス・仕様の未承認・判定の重大な不一致・差し戻しの上限など） | オーナーの判断待ち |

- `merged` に変えてよいのは裁判所と release だけ（MUST）。裁判所が記録としてコミットしてよいのは、その周回に自分で書き換えた票と `_board.json` だけ（MUST。ほかの誰かのコミットしていない変更を裁判所の名前で main に入れない。OBS-044）。書き換える票にほかの誰かのコミットしていない変更が残っていれば、**作業ツリーの票をコミットしてはならない**（MUST NOT。書けば他人の書きかけが裁判所の名前で main に入る。OBS-050）。裁判所は、申請中の票にほかの誰かの書きかけがある間は**その申請を処理しない**（MUST。判定も記録も統合もせず、申請を残して `ticket_dirty_wait` を記録する。確かめるのは処理の始めと、held の記録・統合の直前。p0.4.2）。書きかけがコミットされるか戻されれば、次の周回で普通に処理する。未追跡の票も書きかけとみなし、状態を取れなければ書きかけとみなす。限界：裁判所がその周回に一度書いた票は、その後に人が書いた変更も周回の終わりの記録のコミットに入る。release も起動時の確認の後に票をコミットする。人と裁判所が同じ checkout を使う限り残るので、**裁判所の周回の間と release の間は、人は票を直さない**（運用）。統合の後に票に書けなかったときは `ticket_status_unwritten` を記録し、オーナーが票を直す。
- 差し戻しの上限は3回（取り消された差し戻しは数えない）。上限に達した票の申請は、司法を呼ばずに blocked にする（MUST。判例 G23〜G23g、p0.4.7）。回数は票の「## 6. 記録」から後ろの、裁判所の記録の行の形（`- <時刻> gate-runner: status → in_progress`）を数え、Z3 の裁判所の出来事（`gate_events.jsonl` の `rejected` で `status` が `in_progress`）も JSON として読んで数え、**多い方を使う**（行政は main の票の §6 を書けるが Z3 は書けないので、§6 の行を消しても、対応する出来事が Z3 に残っていれば回数は減らない。判例 G23f〜G23f5）。Z3 の記録を数えられない（読めない行・集計の失敗）ときは 0 とみなさず、申請を残して処理せず `returns_uncountable` を記録する（MUST。fail-closed。判例 G23g）。§6 の行の書き手は確かめないので、§6 に同じ形の行を写せば多く数える（統合を止める側に倒れる）。取り消しは Z3 の `annulments.jsonl` を JSON として読んで、その票の行を1行1回として引く。限界：`gate_events.jsonl` はハッシュチェーンの対象ではなく、同じ機械の管理者は書き換えられる（§10）
- **作業員の起動の窓口**（p0.4.10、D-66・D-67）：作業員（worker）とテスト担当（tester）は、Agent ツールで起動してはならない（MUST NOT。フックがどの役割からも拒む）。起動は、行政の長が `merge-requests/launch/T-NNN.json`（中身は `{"task":"T-NNN"}` だけ。置けるのは行政の長だけ）に申請を置き、Kernel の窓口（`launcher.sh`）が受け付けて夜間の代行（`night-runner.sh --launch`）を1票ずつ動かす。窓口（1つだけ動く。ロック）は、申請のフォルダの親が記号リンクなら何も読まず、申請を記号リンクをたどらずに開いて同じファイル記述子で種類と大きさ（256 バイト）を確かめ、全体がちょうど1つの JSON のオブジェクトであることを確かめる。合わない申請は拒む。受け付けた申請は、Z3 の状態（`launch/state.jsonl`）に「受け取った」を書いてから消し、起動したら pid を書く（申請の正本は Z3。受け取ったまま起動の記録がない票は次の周回で起動する。動いているかは pid のプロセス群の生死で見る）。控えは Z3 の `launch/receipts/` に置く。申請は Bash では置けない（Write ツールで行政の長だけ）。承認・依存・停止・予算の台帳・同時の数・保護パス・前検査は夜間と同じ。1回の作業員の実行は 45 分まで
- **自動修正と前の試行の記録**（p0.4.10）：起動の窓口からの票は、初回＋自動修正3回まで作業員を起動し直す（差し戻しの上限3回とは別に数え、先に達した方で止める）。起動し直すとき、Kernel は前の試行の記録を作業員への指示に添える：①この票のこの申請の後の判定の記録から取り出した司法の指摘（重さ・要件の ID・分類・相対パスと行・短い理由。絶対パス・秘密らしい文字列・メールアドレスは伏せる） ②前の試行で変えたファイル（git の差分） ③前の作業員の報告（**未検証の仮説**と明記する）。前の重い指摘（要件の ID・分類・ファイル）が1つでも残ったまま差し戻されたら、自動修正をせず人へ戻す（MUST）。指摘は、成り立った判定（判定として解釈できた記録）の、いちばん新しい候補のものだけを使う。指摘と報告は引用の囲みに入れ、囲みの中の命令に従わないよう指示する（文字列の検査で注入をすべて防げるわけではない）。前の試行の記録は司法には渡さない（§6 の入力は変えない）。起動の窓口からの票は、オーナーが承認した仕様の範囲で、時刻によらず無人で初回＋自動修正3回まで動く（D-67。unattended の印は求めない）。予算の台帳の試行の上限（attempts_per_ticket）が先に尽きれば、そこで止まる。台帳が起動を拒んだ・時間切れで止めたときは、その票を止める。試行ごとに停止を確かめる

## 6. 司法の独立（成立条件③）

1. 司法の入力は、裁判所が機械的に集めた**差分・main の票の受け入れ条件（または要件の行）・決定論的な監査の結果**だけでなければならない（MUST）。行政の説明（コミットの本文、票の手順の案・記録、作業員の報告、会話）を入れてはならない（MUST NOT）
2. 司法はツールを持ってはならない（MUST NOT）。別系統のモデルの司法（Codex）は、同じ入力の組み立てを使う（SHOULD）
3. 決定論的な監査の不合格・未実行は、LLM の合格で取り消せない（MUST）
4. 二つの司法の判定が重大な指摘で分かれたら、統合せずにオーナーの裁定を待つ（MUST）。裁定は票と申請の SHA に結び付ける
5. **司法が使えないことは判定ではない**（MUST。p0.4.3、OBS-053）。裁判所が読む判定は、この申請の候補の SHA に結び付いた記録だけ（MUST。前の申請の判定を使わない）。記録がない・ファイル全体が1つの JSON でない・結論が APPROVED／CHANGES_REQUIRED のどちらでもない・司法の出力を解釈できなかった（`judge_parse_ok`／`parse_ok` が false。CLI の空の応答・認証切れ・利用の上限）ときは「司法が使えない」とし、統合せず、差し戻しにも数えず、票を書き換えずに申請を残す（`judiciary_unavailable`）。同じ申請の SHA で通算3回になれば blocked にしてオーナーの判断に回す（差し戻しとしては記録しない）。夜間の合格の記録（held）には判定の版と `--no-codex` の有無を残し、release は版の印のない記録と、`--no-codex` でないのに Codex の判定がない記録を統合しない（MUST）。Codex を省けるのは、裁判所を `--no-codex` で起動したときだけ（判定の欠落を「省いた」とみなしてはならない。MUST NOT）
6. 裁判所は起動時に、監査と司法の道具がそろって動くことを確かめ、欠けていれば起動しない（MUST。`preflight_failed` を記録し、申請と票に触れない）

## 7. 統合（成立条件④）

1. main に統合できるのは裁判所（gate_runner）と、朝のオーナーの承認（release）だけ（MUST）。行政は `git merge`・main の参照の書き換え・main への push ができてはならない。**行政の長が main に直接コミットしてよいのは `docs/` の下（票・記録・文書）だけ**（MUST。ソースは作業員のブランチから裁判所を通す。`-a`・パスの指定・`--amend`・作者名を変える `-c` は main では拒否）。作業員は main にコミットできない
2. 裁判所は、申請ごとに最初に取った main の完全な SHA に、仕様の照合・差分・候補・司法・統合のすべてを固定しなければならない（MUST。確認と使用の時刻の差を作らない）。検査した候補のコミット（その SHA ＋ 申請の SHA）だけを fast-forward で統合する。held の記録と統合の直前に、停止と main の前進を確かめ直し、main が進んでいれば検査し直す
3. 差分が保護パス（法律・憲法・CI・票の盤・申請）か `files_allowed` の外に及べば統合しない
4. 夜間（`--hold`）は合格しても統合しない。朝に release が、今の main と組み直した変更が夜に判定した変更と一字一句同じことを確かめてから統合する。release は錠で直列化し（MUST。片方の取り消しがもう片方の統合を消さない）、申請がすでに main に入っていれば何もしない。取り消しは、HEAD がその実行の作った統合のコミットのときだけ行う。統合したら票の status を merged にして、その票だけをコミットする（p0.4.1、OBS-048）
5. 裁判所は周回ごとに、公開してよい集計だけを **Kernel の状態の写し**（`docs/governance/kernel-state.json`、`vgdd.kernel-state.v1`）に書き出す（MUST。p0.4.3）。書くのは裁判所だけ（保護パス。git で追跡しない）。写しは**表示用で、判断の根拠にしてはならない**（MUST NOT。裁判所・夜間の代行・release は読まない）。判定・裁定・停止の理由の本文、証拠ストアの各行、パス、セッション ID、ハッシュ（全桁も一部も）を含めてはならない（MUST NOT）。周回ごとに書き直す（`generated_at` が裁判所の生存の合図）。書き出しの失敗は周回を止めない（`kernel_state_unwritten` を記録）

## 8. 停止と復旧（ADR-010・ADR-027）

1. オーナーは Kernel 全体を止められなければならない（MUST）。停止は Z3 の `STOP`（エージェントは作れず消せない）
2. 停止中、Kernel は読み取りのツール（ファイルを読む・探す）以外のすべての操作を拒否しなければならない（MUST）。**Bash はすべて拒否する**（文字列の照合では、読み取りに見えて書き込むコマンドを見分けきれない）。裁判所は申請を処理せず（周回の始め・申請ごと・held の記録と統合の直前に確かめる。ただし §7-5 の状態の写しに「停止中」を書くことだけは例外として許す。p0.4.3）、夜間の代行は票を取らず、release（票ごと）と仕様の承認は動かない
2b. 停止は、停止の後に始まる操作を止める。**停止の前に始まって実行中の処理（長い Bash、夜間の作業員、司法の呼び出し）を強制終了はしない**（既知の限界。それらの次のツール呼び出しはフックが止める）
3. 再開の前に、少なくとも次を確かめなければならない（MUST）：証拠ストアのハッシュチェーンとチェックポイント、共有の git の設定が基準値と同じ、main の checkout が main ブランチにあり未コミットの変更も未追跡のファイルもない、停止の時点の main（STOP に書いた完全な SHA）が今の main の祖先である、停止の後に main に入ったコミットがない（**作者名にかかわらず**、あればオーナーが一覧を確かめて明示的に受け入れる）。どれかを確かめられなければ再開しない
4. 停止と再開は錠で直列化する。再開の記録を先に書き、その後で STOP を消さずに移す（記録に失敗すれば再開しない）

## 9. 予算（ADR-018・ADR-020、p0.4.9 で台帳を加えた）

- 夜間の代行は、並行数（**既定は1＝逐次**）・1晩の票数・時刻・1票と1晩のトークン・司法の呼び出し回数・空き容量の上限を持ち、上限に達したら新しい票を取らない（MUST）。Max の5時間枠の残量は読めないため、利用上限の文言で止める
- **予算の台帳**（p0.4.9、D-66・D-67）：作業員（夜間の代行）・judge・Codex の司法・憲法審査の呼び出しは、Kernel の窓口（`metered.sh`）を通し、起動の**前**に Z3 の台帳（`budget/ledger.jsonl`）へ予約を書き、終わった後に精算しなければならない（MUST）。台帳が唯一の正本で、実行の状態は台帳から作り直す。窓口は、子が自分で終わった後に同じプロセス群に残った子孫を終わらせ、終わりを確かめてから**子の終了コード**で精算する（中断として扱わない。p0.4.10a、OBS-062）
  - 追記は1つのロックの下で「読む → 鎖と最後の番号・ハッシュの記録（`budget/ledger.head`）を確かめる → 遷移を確かめる → 追記 → fsync → 記録を更新」を1回の処理にする。各出来事は `event_id` を持ち、同じ `event_id` の二度目は効かない（精算の二度目で戻さない）。同じ要求の ID の二度目の起動は拒む（MUST）
  - 窓口は呼び出しを、端末を持たない新しいセッション（新しいプロセス群の長）で動かし（p0.4.9a。端末の上で動く裁判所の下で、子が端末の設定を変えようとして止まらないように）、時間切れ・中断（TERM・INT・HUP・ALRM）を受けたら、プロセス群ごと終わらせ、終わりを確かめてから精算する。終わりを確かめられないとき、起動の記録・精算に失敗したときは、出力を渡さずに拒否として終わる（MUST）。起動の記録のプロセスが生きている間は精算しない
  - 上限は Z3 の `budget/limits.json`（期間の ID・終わりの時刻・全体／1票／1回のトークン・司法の回数・作業員の同時の数・1票の作業員の試行の数）で、書くのはオーナーの操作（`budget-set.sh`）だけ。上限のファイルの欠け・形の違い、期間の外、停止中（Z3 の STOP）、台帳の途中切れ・鎖の不一致・最後の番号とハッシュの記録との食い違い（行の切り詰め・台帳の消失）、実際の消費が予約を超えた記録があるときは、新しい起動をすべて拒まなければならない（MUST。fail-closed）。1回の予約は `tokens_per_run` を超えてはならない（MUST NOT）。期間を変えても、前の期間の起動中・動いている実行の予約と作業員の枠は数え続ける
  - 消費の数え方：利用量を読めた呼び出しは `input`＋`output`＋キャッシュの作成・読み込みのトークン。**読めない呼び出しは予約の全量を使ったものとして数え、0 として扱ってはならない**（MUST NOT）。起動中のまま記録が止まった実行（予約の後に起動の記録も終わりの記録もない）は、生死が不明として予約と作業員の枠を保ち、同じ票の次の作業員を起動しない。起動の記録の後にプロセスが終わったのに終わりの記録がないものは、予約の全量を消費として数える
  - 実際の消費が予約を超えた超過の記録は、その期間の新しい起動をすべて止める。止めを解くのは、オーナーが新しい期間の ID で上限を置き直すこと（`budget-set.sh`）だけ
  - 起動の記録の pid はプロセス群の長で、群の中に1つでも生きているプロセスがあれば生きているとみなす（子が先に終わって孫が残る間も、枠と予約を保ち、精算しない）
  - 予約は起動の判断のための量で、1回の呼び出しが使える量の上限ではない。トークンと金額の厳密な上限は保証しない（サブスクリプションの利用枠の残りは読めない。保証できるのは次の起動を拒むことだけ）
  - 窓口で拒まれた司法の呼び出しは CLI の失敗として扱い、判定は成り立たない（§6-4〜6-6 の「司法が使えない」。合格にしない）
  - 夜間の代行は、作業員の利用量が読めないとき 0 とせず、1票の上限を使ったものとして数える
## 10. 証跡（成立条件⑤、ADR-009）

- 操作の証拠ストア（`tool_calls.jsonl`）は追記だけで、各行が前の行の SHA-256 を持つ（ハッシュチェーン）。裁判所は周回ごとに件数と末尾の行の指紋をチェックポイントとして残し、末尾の切り詰めを検出する。再開の前の検証の対象もこのファイル。裁判所の出来事（`gate_events.jsonl`）などほかの記録は鎖の対象ではなく、途中の行の書き換えは検出しない
- 判定（司法）、承認（仕様・裁定・朝の統合）、停止・再開、外部の前進の検知は、Z3 の記録に残す（`verdicts/`、`spec_approvals.jsonl`、`rulings.jsonl`、`held.jsonl`、`gate_events.jsonl`）
- 裁判所は周回の始めに共有の `.git/config` を基準値と照合し、違えば（または基準値がなければ）申請を処理せずに止まる（MUST。OBS-033）。止まる前に `git_config_changed`（種類だけ。設定の本文とハッシュは残さない）を `gate_events.jsonl` に残し、終了コード 70 で終わる（MUST。p0.4.7、OBS-060：記録なしに終わり、止まったことが約2時間分からなかった）。この記録は鎖の対象ではなく、止まった周回はチェックポイントを作らない。記録先に書けなければ記録なしに止まる（申請は処理しない）。判例 G24・G24b
- 限界：同じ機械の管理者（オーナーの権限）は記録を書き換えられる。外部への固定（アンカー）はしていない

## 11. 適合性（ADR-012・ADR-025）

0. **不変条件**（p0.4.4。ADR-034〜046 の総括の INV-01〜12）：権限の表 `invariants` に、各不変条件の状態（enforced・partial・not_applicable）と、それを確かめる判例を持つ。enforced と partial は判例がすべて合格しなければならず（MUST）、partial は残る穴（gaps）を、not_applicable は理由を書く。適合性テストの INV 群が自己検査する

- 適合性テストは `vgdd/conformance/run.mjs`。群と成立条件の対応：C1（役割分離と権限）→①④、C2（仕様の統治）→②、C3（独立司法）→③、G（裁判所の場面）→②④、H（行政の長の main へのコミット）→④、K（停止と再開）、N（夜間の代行）、A（証跡）→⑤、M（権限の表の自己検査：どの権限にも確かめ方があり、参照した試験が合格している）
- テストは、止めるべき操作が止まることと、**通すべき操作が通ること（陽性の対照）**の両方を試さなければならない（MUST）。前の版の実装に対して実行し、新しい規則の試験が実際に落ちることを確かめる（試験が空回りしていないことの確認）
- 配置済みの設定（`.claude/settings.json`）は、原本 `vgdd/settings.v2.json` の拒否の規則・sandbox の書き込みと読み取りの禁止の一覧をすべて含み、sandbox の `enabled`・`failIfUnavailable`・`allowUnsandboxedCommands` は原本と同じ値、フックは同じ構造でなければならない（MUST。p0.4.8、判例 ST16）。案件ごとに足してよいのは、拒否の規則と禁止の一覧の項目だけ（フックの追加や置き場所の変更は ST16 に通らない）。ほかの項目（allow・ask・network など）は比べない。`run.mjs --impl z3` が試す写しの場所は `VGDD_Z3_DIR`（なければ既定の場所）で、`--record` の書き先と同じ（p0.4.8、判例 ST17）
- 「VGDD Core に適合」とは名乗らない。名乗れるのは「この構成で、適合性テスト N 件に合格（実装と日時）」だけ。権限の表の promise と known_gaps は適合の主張に含めない

## 12. 保証できないこと

- フックの Bash の判定は文字列照合で、回避の余地がある（書き込みは OS の sandbox が最後に止める）
- 人が承認画面で許可した操作は止められない（記録は残る）
- 裁判所の周回ごとの事後検知（`main_advanced_outside_gate`）は、作者名が `gate-runner` のコミットを除いて数える。作者名は偽れる。行政の長が作者名を変えるコミットはフックが main で拒否するが、フックの Bash の判定は文字列照合で、回避の余地は残る（再開の確認は作者名を使わない）
- 行政の長が main の checkout でソースを**書く**こと自体は止めていない（コミットできるのは docs/ の下だけ。書いたソースは裁判所を通らない限り main に入らない）。票の §2 を起草すること自体も止めていない（効力は §4 の承認で縛る）
- Kernel の状態の写しの書き出し先（`docs/governance/`）は、フックと sandbox で行政の書き込みを止めるが、同じ利用者の権限で動くプロセスが書き出しの途中に親を差し替える競合までは防がない（写しは表示用で判断の根拠にしないので、偽の表示は main に入らない）
- 適合性テストは、司法の出力の変換（本物の judge.sh・judge-codex.sh に偽の CLI）と、裁判所が書いた held を release が読む一続き（L12・L13）を試す。本物の司法から裁判所・held・release までを1本で通す試験と、状態の写しを書き換えても判断が変わらないことの動作の試験（ST9 は参照の検査）はない
- release は held を Z3 の判定の記録と票に照合し直すが、`no_codex: true` の held では Codex と security の照合を省く。Z3 の held を書き換えられる者（オーナーの権限）はこの省略を使える。Z3 に書けない行政からの突破ではない（Codex の5回目の監査。直すなら裁判所の起動の省略モードを held とは別の記録に固定する）
- チェックポイントの照合（p0.4.5、OBS-055）：件数 N の行のハッシュが違っても、N+1 行目のハッシュと一致し、ハッシュチェーン全体が無傷なら、記録の取り方の競合（p0.4.2 までの裁判所の不具合）として注記にとどめ、検証の失敗に数えない。保証の範囲：チェックポイントが変えられておらず SHA-256 が安全なら、このチェックポイントは N+1 行目までを拘束する（判例 A8〜A15）。どのチェックポイントにも固定されていない末尾は保証しない（通常のチェックポイントと同じ）。ほかの形の食い違いは今までどおり失敗。状態の写しの `checkpoint_mismatches` は失敗に数えた食い違いの件数で、競合の注記は含まない（Kernel の区画の「チェックポイントの食い違い」の数も同じ意味。競合の注記は verify-chain の出力にだけ出る）
- フックの Bash の照合は文字列で、変数や引用で分けたパス（例：`p=governance; cp x "docs/$p/…"`）への書き込みは拒否しきれない。`docs/governance/` への書き込みを最後に止めるのは OS の sandbox（`.claude/settings.json` の denyWrite）で、その阻止は実際のセッションで確かめる（適合性テストの範囲外）
- 監査の sandbox が読ませない秘密は、裁判所の --repo の `.env.local`（起動の時点で絶対・正規化したパス）だけ。`.env.local` 自体がシンボリックリンクのときのリンク先、夜間の代行（night-runner）の --repo は対象にしていない（p0.4.6 の限界）
- 承認の法律の系統（INV-06）は、ref に権限の表がない（`ls-tree` で空）ときは結び付けない（法律を持たないリポジトリのため）。権限の表は保護パスで、行政は main から消せない。取り出しに失敗したときはどの承認も効かない
- 状態の写しの不変条件ごとの結果は、稼働中の Z3 の実装と指紋が同じ適合性テストの記録だけを使う。指紋は法律のスクリプト・フック・証拠の検証（verify-chain）の中身で、エージェントの定義・権限の表・Node や git の版・設定は含まない（それらを変えた後も、スクリプトが同じなら前の結果を検証済みと表示しうる）
- 司法の出力は、本文全体が1つの JSON（全体を ```json で囲むのは許す）で `vgdd.verdict.v1` に完全に合うときだけ判定として成り立つ。説明の文を前後に付けた判定は「司法が使えない」になり、同じ申請で3回続けば blocked になる（fail-closed の側に倒す）
- Kernel の状態の写しが Z3 の記録と一致することは、Z3 を読めるオーナーの照合に依る。作業員（worker・tester）の起動を承認の後に限ることは、p0.4.10 から起動の窓口（night-runner --launch の承認の照合）とフック（Agent・claude の CLI での起動の拒否）で強制する。ただし、行政の長が作業員を使わずに自分で書くこと、worker・tester 以外のサブエージェント（汎用の補助など）に実装を頼むことは止めない（どちらも、main に入るには裁判所と release を通る）
- 司法の判定の正しさ（LLM）は保証しない。二つの系統の司法が同じ見落としをする可能性は残る
- 予算の台帳（p0.4.9）が数えるのは、窓口（`metered.sh`）を通る呼び出しだけ。p0.4.10 で作業員とテスト担当の Agent ツールでの起動はフックが拒む。**行政の長・立法補佐・オーナーのメインのセッション（行政の長が作業員を使わずに自分でコードを書くことを含む）、worker・tester 以外のサブエージェント（調べもの・点検）、アプリの中の AI の呼び出しは、台帳の外**。起動の窓口の受け取りは、申請のフォルダの親の同一性を操作の前に確かめ直すが、同じ利用者の権限で動くプロセスが確かめた直後に親を差し替える競合までは防がない（行政の Bash からの書き込みは、フックの照合と sandbox の denyWrite（`merge-requests/launch`）で止める）。CLI での起動の拒否は Bash の文字列の照合で、変数や別名で組み立てたコマンドは見分けきれない。起動の窓口が子を起動してから状態に記録するまでに落ちたときは、runner が自分の pid を状態に書く。それでも runner が二重に起動したときは、同じ票の作業員が同時に動くことは予算の台帳が拒むが、時間差のある重複の作業（片方の作業員が終わった後に、遅れたもう一つの runner が作業員を起動する）は防がない。main の checkout への票のコミットは runner どうしでロックを取り、票のパスだけをコミットするが、裁判所の票の編集・コミットとの競合は防がない（同じロックを使っていない）。フックの判定は Agent ツールの `subagent_type` の名前によるので、同じ働きの別の名前の定義を作られると止められない（エージェントの定義は保護パスで、行政は書けない）。前の試行の記録の伏せ字は文字列の照合で、すべての秘密を見分けるとは限らない（作業員への指示にだけ使い、公開しない）。Codex の利用量はまだ読まず、予約の全量で数える。台帳・最後の番号とハッシュの記録・ロックは同じ利用者の権限で書けるので、オーナーの権限を持つ者の書き換えは防がない（鎖の不一致と、記録との食い違いは検出する。台帳と記録を一緒に消す・差し替えることは検出しない）。窓口が `SIGKILL` で止められたときは子を終わらせられない（子は動き続け、生きている間は枠を保つ）。プロセスの ID の再利用で、終わった実行を生きていると見ることがある（枠を保つ側に倒れる）
- 同じ機械の管理者権限を持つ者に対する完全な防御と、記録の不変性は保証しない
