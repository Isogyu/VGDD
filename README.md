# VGDD Governance Kernel

**AI のチームに開発を任せても、仕様の承認・裁定・停止は人が持つ。役割ごとの権限と承認の条件を、プロンプトではなく実行環境で制御する開発統治の仕組みと、その実運用の集計・票の記録・検証結果の可視化。**

Built with Claude: Japan 2026 の提出作品です。題材のアプリ「つぶやき業務ログ」を、この仕組みのもとで AI のチームが実際に開発しました。画面に出すのは、そのときの実運用の集計・票の記録・検証結果です。

## 課題

AI に開発を任せる範囲が広がるほど、人は「何を作らせるか」「作られたものが条件を満たすか」「危ないときに止められるか」を握り続けにくくなります。AI への指示文に「してはいけない」と書いても、守られる保証にはなりません。

対象は、複数の開発 AI に作業を任せ、仕様の承認と統合の判断を1人で担う開発者です。未承認の統合や判定の欠けを毎回手で確かめる負担を、実行環境の強制に置き換えることを狙います（削減の効果は未測定）。

この作品が扱う問いは、**AI に開発を任せるとき、人はどう主権を保つか**です。答えの案として、次の形を実際の開発で運用しました。

- 人（オーナー）が承認していない票の統合を、裁判所が拒否する。夜間は着手も拒否する。昼の着手を承認の後に限ることは運用上の約束（法律 p0.4.0、2026-11-05 から。[SPEC §12](vgdd/kernel/SPEC.md)）
- 実装の文脈を持たない2つの系統（Claude と、別系統の Codex）が、差分・受け入れ条件・監査の結果だけを見て判定する
- main に統合できるのは裁判所のプロセスと、オーナーが動かす release だけ
- 統治の仕組み自身の穴も、判例（再現する試験）にして、人の承認を経て直す

**構築の記録と、想定する運用は分けて読んでください。** この開発の記録は、Claude の司法に Codex の第2の司法を加えた構成で生まれました（judge と Codex が分かれて人が裁定した件もこの構成）。本来の運用は、1つの Claude アカウントで、役割・道具・文脈を分けたセッションに立法・行政・司法を担わせる想定です。その構成での司法の独立性は確かめていません。第2の司法は、別系統・判定の形式・fail-closed の条件を満たせば差し替えられる設計で、社外にコードを出さない運用に向けてローカル LLM も候補にしています（未検証）。

もう1つ、オーナーが全体を止める仕組みも持っています。停止の後に始まる操作を止めることを判例で確かめ、本番でも停止・拒否・再開を1回確かめました（2026-11-07 01:29〜01:31。[`docs/validation.md`](docs/validation.md) §4）。

### この文書の語

| 語 | 意味 |
|---|---|
| オーナー（市民） | 目的と制約を決め、承認・裁定・停止をする人 |
| 立法補佐 | 法律と票を起草する役の Claude。起草に効力はない |
| 行政の長・作業員 | 作業員を起こして申請する役と、隔離した場所で実装する役の Claude Code |
| 司法 | judge（Claude）と Codex。合否を判定し、ツールを持たない |
| 裁判所 | 監査と司法を動かし、合格を統合するスクリプト（`gate-runner.sh`）。sandbox の外で動く |
| Kernel | 決めた規則を実行時に強制する部分の全体。LLM で判断しない |
| 票 | 1つの作業の受け入れ条件と記録を書いた文書 |
| 判例 | 穴や規則を再現する、適合性テストの試験 |
| held | 夜間に合格し、オーナーの統合の承認を待っている状態 |
| Z3 | 作業フォルダの外の保護領域。承認・判定・証拠を置き、開発エージェントは読めず書けない |

## 可視化（`/governance`）

統治の様子を、実運用の集計・票の記録・検証結果で見せる画面です。証拠ストアと判定の本文は公開せず、件数とリポジトリの記録だけを出します。

画面の記録は、出来事の時刻・担い手・状態だけを出します。票の §6 の記録の文（SHA や判定の要約）は、画面にも `GET /api/governance` にも出しません（T-034。11/7 19:48 に main 4ebc0b1 の作業ツリーで確かめた）。

| 区画 | 見せるもの | データ | 状態（2026-11-07 19:50） |

| 統治の全体図・停止の全面表示 | 市民・立法・行政・司法・Kernel の5つと生きた数字、停止中の赤い帯 | 状態の表示用ファイル、票の盤、操作の集計 | 統合済み（T-026） |
| Kernel | 稼働／停止、法律の版、成立条件、承認、held、裁定、判定、ハッシュチェーン | 状態の表示用ファイル | 統合済み（T-022） |

## 再現

clone で試すこと、作者が別の場所に構築すること、ほかの人が既存の案件に入れることは、別の話です。**確かめたのは clone で試すことだけです。** 3つの違いと導入の確認の表は [`docs/adoption.md`](docs/adoption.md) にあります。

### clone してできること

前提：Node.js 24 以上（適合性テストだけなら 22 以上）、git、`jq`、`shasum`、UTF-8 のロケール。確かめた環境はオーナーの macOS だけで、Linux は未確認です。

```bash
node vgdd/conformance/run.mjs   # 適合性テスト。npm の依存なし。LLM は呼ばない。使い捨ての試験用リポジトリの上で動く
npm ci
npm test                        # 題材のアプリと画面の開発用テスト
npm run dev                     # 動かしたまま http://localhost:3000/governance を開く
```

- **画面**：統治の数字・票の盤・票1枚の運命・法律の歴史は、リポジトリの記録から出ます。
- **全体図と、Kernel・不変条件の区画**：状態の表示用ファイルがリポジトリに入らない（`.gitignore`）ので、clone では全体図の一部の数が「—」になって黄色の帯が出て、Kernel と不変条件の区画は「書き出しがありません」になります。実際の値は動画で見せます。提出の時点の写しは [`docs/governance/snapshots/submission/`](docs/governance/snapshots/submission/) にあり、統治シアターから読むためのものです（今の写しは 11/7 02:03、法律 p0.4.5。機能凍結の直前に取り直します）。
- **題材のアプリ**（`/`）：`npm run dev` を動かしたまま、別のターミナルで `npm run seed` を実行すると合成データが入ります。API キーがなければ、保存済みの Claude の出力を再生するだけで、任意の入力には応答しません（合成データの3つの作業の、作業終了後の整理だけ。途中の整理・手順書の原案・AI の検出は再生の記録がなく動きません）。
- **確かめた範囲**：一時的な clone（main `f786d2f`、2026-11-07 01:5x、macOS、Node 25）で、`npm ci`・適合性テスト 387/387（当時の法律 p0.4.5）・`npm test`・`npm run typecheck`・`npm run lint`・`npm run build`・`npm run dev`、デモ用データの投入（`POST /api/dev/seed`）、`/governance` の表示まで通りました（[`docs/validation.md`](docs/validation.md) §4）。今の版の clone と `npm run seed`、Windows・Linux、ほかの人の手元は未確認です。

### できないこと

**Kernel の実稼働は、clone だけではできません。** 強制の実体は作業フォルダの外に置く保護領域（Z3）と、sandbox の外で動かす裁判所にあるからです。準備の中身は [`docs/adoption.md`](docs/adoption.md) に書きました。

## 実証

主張と証拠の対応は [`docs/validation.md`](docs/validation.md) にまとめました。代表例は次の3件です。

1. **例1**：承認は、承認した対象と範囲にだけ効く
2. **例2**：司法が使えない状態は合格ではない
3. **例3**：統治の仕組み自身の失敗を、判例にして正規の改正で直す

### 誰の、どの負担が軽くなるか

AI に開発を任せる人の、「判定が本当に成り立ったか」を毎回見張る負担です。

例：前の版（p0.4.2）に試験をかけると、片方の司法の判定が欠けても、もう片方の合格だけで統合されました（判例 G15・G19）。p0.4.3 で「司法が使えない状態は合格としない」規則を入れ、同じ試験で統合されないことを確かめました（[`docs/validation.md`](docs/validation.md) 例2）。これは試験での確認で、本番で防いだ件数は数えていません。

比較実験はしておらず、負担や時間の削減率は未測定です。

## 限界

全文は正本にあります。

- [`vgdd/kernel/SPEC.md` §12](vgdd/kernel/SPEC.md)：保証できないこと
- [`docs/kernel.md` §4b](docs/kernel.md)：不変条件の状態。**一部**は INV-03・07・08・11、**対象外**は INV-09。ADR-034〜046 の「一部」「最小形」「未」も同じ節にあります

読む前に知っておいてほしい主な点です。

- フックの Bash の判定は文字列照合で、回避の余地があります
- 人が許可した操作は止められません
- 司法は LLM で、判定の正しさは保証しません。2つの系統が同じものを見落とすこともあります
- 同じ機械の管理者権限を持つ人は、Kernel と記録を変えられます
- 停止は、停止の前から動いている処理を強制終了しません
- 本番の停止と再開で確かめたのは1回だけです。第三者による再現はまだです（[`docs/validation.md`](docs/validation.md) §4）
- 実際の sandbox と起動設定を確かめたのは、2026-11-03 の実セッション（フック p0.1.2〜p0.2.0、[`docs/vgdd-status.md`](docs/vgdd-status.md)）です。適合性テストの範囲外で、今の版では実セッションの迂回の検証をやり直していません
- 題材のアプリは合成データで使うものです。機密の検査はパターンの照合で取りこぼしがあり、ログイン・認証はありません
